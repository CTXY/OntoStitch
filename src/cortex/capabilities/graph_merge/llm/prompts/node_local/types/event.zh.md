# 本组类型 Guidance：Event

## 1. 整合目标

整合同一业务发生**类型**的定义、角色与范围，保留“发生了什么、谁参与、时间/地点及作用对象如何关联”。共享日期列、参与者或 JOIN 路径不证明类型相同；“申请”与“批准”等实际不同类型应交回 Identity。

## 2. 字段填写规范

- **`properties.definition`**：必填非空文本，说明业务发生、范围与已知粒度。
- **`properties.targets`**：可选二维物理 ID 列表；每个内层为完整匹配，非空且组内不重复。不同匹配方法不拼成联合组；外层“同组＋同表达式”不得重复。
- **`properties.target_expressions`**：可选对象；键为规范、不越界的 targets 下标字符串（`"0"`、`"1"` 等），值为非空完整条件/关联表达式。组重排后同步重编号；无 targets 或 targets=[] 时不留表达式条目。
- 事件可以通过已有业务关系连接已绑定 Concept，不为覆盖字段而编造 targets，也不把日期非空当成完整事件发生判据。

---

## 3. 合并、泛化与冲突

- 同一事件类型的互补角色说明和相容匹配方式可以整合；保留角色之间的配对，不只保留孤立参与者字段。
- 请求中的参与者或时间窗可作为筛选参数保留；事件定义中固定的参与含义或业务范围不能泛化掉。
- 同一类型在重叠范围内有已证实的不兼容定义或角色关联时，保留完整分支，不跨分支拼参与者与发生条件。必要前提不足时补来源，不凭邻近字段猜测。

### 完整内容示例

假设来源确认同一订单提交发生，一份说明客户主体，另一份说明订单对象，且原关系确认二者配对，可写为以下 `NodeContent`：

```json
{
  "name": "订单提交",
  "description": "客户向系统提交订单的业务发生类型，以订单为粒度。",
  "aliases": ["下单提交"],
  "tags": ["订单流程"],
  "properties": {
    "definition": "客户提交一份订单；客户是主体，订单是作用对象，二者属于同一提交发生。"
  }
}
```

本例的原角色关系继续继承；若实际输入有有效 targets，须照实保留，不因本例省略可选字段而删除。
