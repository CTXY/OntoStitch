# 本组类型 Guidance：Concept

## 1. 整合目标

整合同一业务对象、类别、属性或术语的定义与完整匹配方法。保持表示角色：例如学校可由代码或名称表示，但“学校实体”不自动等于“学校名称属性”，代码/名称也不自动成为可互换的计数依据。

## 2. 字段填写规范

| 字段 | 填写要求 |
| --- | --- |
| `properties.definition` | 可选；有必要时表达统一定义、角色与区分条件，不否定仍有效的来源含义。 |
| `properties.targets` | **非空二维物理 ID 列表**；每个内层是一套完整联合匹配方法，不同外层组是不同方法，不是默认 `SELECT` 列清单。 |
| `properties.target_expressions` | 可选对象；以当前外层组的下标字符串为键，如 `"0"`、`"1"`，值为该组必要的完整条件/关联表达式。 |
| `properties.mapping_type` | 可选字符串；相容时归一，实质差异在定义或分支中保留，不改成数组。 |
| `properties.relation_metadata` | 可选既有关系分组；规则见下文，不代替真实边。 |

### 匹配组校验

- 使用本轮允许的真实物理 ID；组内非空且不重复，不用自然语言列名代替 ID。
- 保留相容的完整组，不将独立方法拼成一个联合组。判重同时比较端点与表达式；同端点但条件不同不等于重复。
- 重排或去重后同步重建表达式索引；键须规范且不越界，值为非空文本。表达式保留条件，使用目录 SQL 名称或已声明别名，不用 graph ID 作 SQL 标识符，不引用组外物理列。
- `targets` 不自动创建 `grounded_on`。解决直接绑定边问题也不能误删有效匹配方法。

---

## 3. 合并、泛化与冲突

- 同义定义或相容补充可以重写为完整定义；相容代码/名称表示保留为独立匹配组，并说明角色。
- 固定业务定义不作为偶然参数删除，例如不能将“已完成订单”泛化后丢掉完成状态。
- 当前没有通用请求参数选择器。互斥匹配方案不能靠一句“按上下文选择”扁平并集；现有字段无法表达时，保留已证实的完整竞争定义或报告缺少前提。
- 不兼容定义或匹配解释按公共契约保留完整分支，分别保留其匹配组与表达式。

### 完整内容示例

假设来源确认学校代码与学校名称表示同一学校实体，可写为以下 `NodeContent`；实际 ID 以本轮输入为准：

```json
{
  "name": "School",
  "description": "学校实体；代码用于标识，名称用于显示，不据此假定名称唯一。",
  "aliases": ["学校"],
  "tags": [],
  "properties": {
    "targets": [["column.schools.code"], ["column.schools.name"]]
  }
}
```

不能将这两组改为一个联合匹配组。若后续调整组顺序，原组的 `target_expressions` 必须随之重编号。

## 4. `relation_metadata`

每项仅为 `{"id":"...","edges":["edge-1","edge-2"],"description":"组合关系含义"}`。节点内 ID 唯一，至少两条不重复的真实相邻边；同谓词、相对 owner 同方向，且作用域可共同成立。

只有该字段显式引用的关系才需补入必要材料。保留其组合含义，不新建边、不组合互斥分支的边；无法自动映射的语义问题交 `relation_followups`。
