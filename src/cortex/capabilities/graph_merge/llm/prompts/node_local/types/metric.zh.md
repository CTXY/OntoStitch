# 本组类型 Guidance：Metric

## 1. 整合目标

整合同一业务数量的完整计算口径。保留来源已承诺的公式、操作数含义、总体、单位、粒度、`NULL`/零值行为和计算次序；名称相近不证明计算等价。

## 2. 字段填写规范

- **`properties.expression`**：必填对象，仅含 `expr`、`refs`。`expr` 为非空计算表达式，非完整 SELECT；`${key}` 占位符集合须与 refs 的键完全一致，refs 将键映射到真实节点 ID。
- **计算校验**：裸列、纯 CAST、仅用 `+0`、`-0`、`*1`、`/1` 包装的恒等表达式会被拒绝。历史输入不符合契约时报告问题，不编造 SUM 等运算过校验。
- **`properties.pattern`**：可选计算说明，与公式同义，不能替代公式中缺少的运算或条件。单位、粒度等必要含义放在已有说明字段，不新增未声明属性。
- **`properties.sql_generation_plans`**：可选列表，每项仅 id、application、steps。id 匹配 `[A-Za-z][A-Za-z0-9_]{0,99}` 且不重复；application 为非空文本、去首尾空白后最多 500 字符；steps 为 1–8 条非空文本，每条去首尾空白后最多 600 字符。

---

## 3. 合并、泛化与冲突

- 相同计算的互补解释、名称和等价计划可以整合；多计划共存需保留各自适用前提。不得从不同口径拼装公式或混用 refs。
- 请求时间窗、展示或排序选项仅在不属于固定口径时可泛化；固定总体、阈值、单位缩放和计算不能丢弃。`${key}` 绑定节点，不是任意请求参数系统。
- 保留真实运算：`SUM(price / amount)` 不自动等于 `SUM(price) / SUM(amount)`，不能因名称含“平均”就把 SUM 改为 AVG。已证实同范围口径不兼容时保留各自完整公式与说明。
- 不替换尚未确认等价的操作数。如果操作数身份影响当前公式是否可合并，报告这项具体前提；不能仅因邻居未来可能合并就改 refs，也不能把未解决的内容问题留成普通关系事项。

### 完整内容示例

假设来源确认同一订单范围、粒度与求和公式，一份提供中文名称，另一份提供等价英文名称，可写为以下 `NodeContent`：

```json
{
  "name": "订单支付总额",
  "description": "对来源确认范围内的订单支付金额求和，保留原订单粒度与 SUM 行为。",
  "aliases": ["Total order payments"],
  "tags": ["支付金额"],
  "properties": {
    "expression": {"expr": "SUM(${amount})", "refs": {"amount": "column.orders.amount"}}
  }
}
```

实际引用须来自本轮输入；不能用示例为原本没有求和的来源新增计算。
