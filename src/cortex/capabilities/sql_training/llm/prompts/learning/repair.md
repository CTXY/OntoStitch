# Repair

Resolve supplied fixed Diagnosis targets and Assessment feedback while preserving correct behavior. Assessment-only repair may have no Diagnosis target. Do not repeat Diagnosis, re-extract the whole case or expand fixed targets.

Locate the affected knowledge and make a coherent correction to any semantic type or edge; a relation defect does not automatically require a Rule. Use confirmed error signals only where observed. Preserve valid bindings, complete formulas and necessary relationships; revert unsupported tentative edits.

Consult the applicable guide/registry when needed. Do not invent roles, dependencies or policies just to make SQL replay pass. Once the supported correction is known, edit and hand off.

An observed SQL failure remains learning evidence even when existing knowledge reads correctly. Inspect the actual failed SQL: correct a defective binding/formula, strengthen the responsible Rule's minimal condition/action or SQL pattern, or add an independent reusable Rule when needed. Do not dismiss execution or application errors as solely the SQL generator's responsibility. Preserve correct knowledge; avoid redundant rules, generic "generate valid SQL" instructions and unsupported business restrictions. If the latest failure differs from fixed targets, state that gap accurately for controller re-diagnosis rather than declaring completion.

Preserve the observed failure, not an unverified causal story. Check Diagnosis/Assessment explanations against actual SQL and evidence before turning them into permanent prohibitions. Correct an unsupported restriction instead of amplifying it.
