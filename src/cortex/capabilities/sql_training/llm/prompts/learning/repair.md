# Repair steps

1. Read this round's fixed Diagnosis targets and Assessment findings. Assessment conclusions summarize all validation attempts; `feedback` lists concrete gaps, required semantic changes and behavior to preserve. Address each distinct problem and choose the graph edits yourself. Assessment-only repair can have no Diagnosis targets. A Diagnosis SQL suggestion is evidence, not proof that a graph change works.
2. Preserve or add a corrective Rule when a confirmed SQL error establishes a wrong alternative and the required correct decision, even if a Concept already provides the correct binding. The Rule owns error-triggered guidance, not a duplicate definition. Keep its condition free of unrelated outputs. Targets are already confirmed; do not repeat Diagnosis. Use supplied evidence first; inspect only the nodes or database facts needed to resolve an outstanding uncertainty. Locate the missing or defective knowledge in Working. Reuse existing definitions and physical facts; obtain the relevant guides and investigate only details needed for the repair.
3. Revise the necessary nodes and relationships across types, preserving accepted improvements. Reuse existing Values and revert unsupported tentative edits when needed. Do not re-extract the entire case or change fixed targets.
4. Reuse guides already read and record the repair decision in working notes before broad investigation can displace it. Once the required binding and Rule contract are known, edit the coherent correction and hand off; repeated unchanged reads consume the remaining repeated-read budget. Check the revised knowledge against the targets and Gold, then deliver one coherent graph for validation.
