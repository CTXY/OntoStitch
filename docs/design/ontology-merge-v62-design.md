## 1. 最重要的语义边界

**Identity 判断只回答：是否指向同一业务对象、业务量、事件含义或独立生成义务。**

- 差异改变业务身份：不得同义合并；允许保留不同节点并建立有依据的业务关系。
- 差异只改变同一身份的描述、匹配实现、计算实现、适用实现条件或业务口径：保持同 identity，送入内容整合阶段处理。
- 不能因为同一身份的内容冲突而另建 identity，也不能因为名字/端点相同而把不同身份的节点合并。
- 若内容分析发现原先身份判错，返回身份判断并纠正；不能仅因内容难以统一就推翻 identity。

例如：来源明确在定义同一项业务指标时，不同公式或口径属于该指标的内容差异；来源明确分别请求不同业务量时，才是不同 identity。分子、分母、粒度、单位等是理解身份的材料，不是自动拆分身份的确定性规则。

这一边界需要同时出现在 Merge Agent 与 Assessment 的契约中。不能让 identity 阶段预先承担“这些实现是否兼容”的判断。

## 2. 任务、动机与输出

输入为已有全局图 G、同一数据库范围内的一批 case graphs H、原始 NLQ/SQL 及可读取的数据库证据 E，以及 ontology 契约 K。

正常知识输出只有整合图：

\[
G^*=Merge(G,H,E;K).
\]

来源映射、检查记录、checkpoint 是运行管理数据，不作为另一类知识产物。不同身份正常分开保存；同身份的真实竞争保存在图内。没有正常的 U 集合，也不把 uncertain 当作默认语义结果。

执行失败、工具不可用、预算耗尽、无法表达必要结果不能被包装为成功。它们属于运行未完成，可重试/恢复；这不等于承诺任何相互矛盾的约束组合都能被自动满足。

目标是：确认重复身份，解释跨 case 差异，整合兼容内容，保留真实竞争，修复来源明确反驳的抽取错误，并维护节点与关系的正确组织。不是最少节点优化，不要求唯一层级或全图无环。

三项挑战及其对应设计：

| 挑战 | 对应设计 |
|---|---|
| 同身份异表达、不同身份共享名称/实现/关系 | 关系感知的候选召回与业务身份判断 |
| 差异可等价、互补、条件化、竞争或错误，表面差异不解释原因 | 共同含义—差异解释—处理决定—完整候选 |
| 身份、内容和图组织相互影响，既不能一次锁死，也不能反复全图推理 | 问题驱动读取、局部事务、影响检查与批次候选刷新 |

核心 idea：**用来源支持的差异解释指导内容与关系的联合整合；提交后的知识用于更新下一轮匹配上下文。**

## 3. 运行组成与总流程

仅两个语义角色：Merge Agent 与独立 Assessment。控制器负责确定性管理，工具提供读取、检索和受限数据库查询。下列步骤不是新增多个 Agent。

```text
1 输入准备与任务建立
  → 2 候选召回和必要上下文读取
  → 3 业务身份判断
  → 4 同身份内容差异分析 + 关系/结构差异分析
  → 5 构造完整局部整合提案
  → 6 代码预览 + 独立 Assessment
  → 7 原子提交 + 影响传播 + 候选刷新
```

反馈回路：读取不足回到 2；新证据证明身份错误回到 3；解释或输出错误回到 4/5；提交改变上下文后回到 2。内部修订有限次，批次刷新也有预算；代码管理是否重启，避免重复调用。

## 4. 步骤 1：准备输入并建立任务

### 输入

G、H、来源目录及固定 root 契约。

### 执行

1. 保留原始 case 图与来源，不改写其历史记录。
2. 用 `(source_graph_id, local_id)` 区分输入节点、边和本地谓词。
3. 按数据库身份对齐 Table、Column、DimensionValue。Value 身份包括 owner column、类型与原始值；显示名称不是身份依据。
4. 本地谓词先按来源区分，避免同名不同契约在 Agent 读取前被拒绝；root 契约不可重定义。
5. 建立名称/内容/物理端点/邻域检索索引，以及节点、边、契约的反向引用索引。
6. 将全部 incoming 语义节点、显式边和本地契约列入处理范围；仅新增边或谓词也要处理。

### 代码与 Agent 分工

代码执行 ID 管理、已知物理身份匹配、索引与初始队列。不在这里判断语义节点同义；不按业务名称做 case-specific 修复。物理身份不能可靠确定时先检查目录证据，不能凭字段同名跨数据库合并。

### 输出与进入条件

获得可追溯输入和可读取的任务目录。必要输入格式、source 访问和物理引用可解析；不要求提前完成全部语义校验，也不能让预处理把需要修复的跨图关系差异直接丢弃。

## 5. 步骤 2：召回候选并读取必要上下文

### 输入

当前 task、当前 working graph、尚未提交的本批输入。

### 执行

1. 取 seed 节点；对 edge-only 任务，以相应端点及待加入关系的局部预览作检索起点；对 predicate-only 任务查契约与使用者。
2. 从三类信号召回：名称/描述与行为内容、物理绑定/输入、已解释的关系角色与邻居。
3. 将已知 Concept 直接端点争用加入 mandatory 比较集合；普通相似候选可 top-k，mandatory 项不可截断，可分页。
4. 提供候选定义、相关边摘要、关系契约及来源目录。未提交 incoming 也参与检索，排除 self。
5. Agent 按具体问题请求补读：要区分什么解释，需要哪个对象/来源，这项信息会影响哪个决定。
6. 工具记录实际返回内容、版本、分页完整性；不得把 missing/too_large 当作已读取证据。

\[
C(n)=C_{mandatory}(n)\cup C_{soft}(n).
\]

mandatory 只来自 Concept 直接绑定独占等已知必须处理的约束，不把 Metric 共享输入当独占违规。targets 重合仍允许；约束针对直接边。

### 关系信号

比较 `(方向, 关系含义, 相邻对象, 适用范围)`，而非只比较 edge_type 名称。相同角色用于候选召回和解释，但同一个主体可具有多个不同对象充当同类角色，不默认函数性。缺边不是否定。

已确认的对齐可辅助后续判断；待确认对应只能作为联合假设，不能彼此循环自证。

### 最小必要读取

实际裁决的候选完整定义、用于论证的关系契约与依赖含义、被引用的来源内容，必须实际可读。改动关系组时读取完整该组；不扩展其 owner 的所有其他关系。代码完整掌握反向引用目录，但不将全部消费者正文塞入 prompt。

### 分工与输出

代码决定检索范围、分页、mandatory 列表及读取记录；Agent 决定需要哪项业务含义才能区分当前解释。输出是局部分析上下文，不是最终匹配结果。

本阶段可结束读取并进入分析，但不等于允许提交；后续 Assessment 可指出具体缺项并要求补读。

## 6. 步骤 3：判断业务 identity

### 输入

候选定义、关系上下文和实际来源。

### Agent 执行

1. 写出拟同义组的共同业务所指或独立义务，不能只说“都是学校相关”或“都使用聚合”。
2. 列明不能丢弃的身份限定：对象角色、事件含义、明确请求的业务量/义务等。
3. 逐项判断关键差异属于身份变化，还是同身份的描述/实现/口径差异。
4. 对拟合并的整个组检查共同身份是否成立，不能用相似性传递闭包代替组级判断。
5. 需要更多信息则提出具体读取；形成有理由的同义整合组或身份区分，不以 unknown 作为常规终点。

| 类型 | 身份判断对象 | 留到内容阶段的差异 |
|---|---|---|
| Concept | 同一业务所指、对象/类别/属性角色 | 同一所指的描述、绑定及定义口径 |
| Metric | 同一被定义的业务量 | 该量的公式、实现、单位表示及口径差异 |
| GenerationRule | 同一最小独立生成义务 | 实现该义务的动作细节、条件化策略及策略竞争 |
| Event | 同一事件含义及参与角色 | 该事件的描述、锚定或关联表达差异 |

上表不是按字段机械划分。比如粒度差异若来源明确表示不同被计量对象，则身份不同；若来源明确仍在定义同一业务量，则属于内容分析，不能按 grain 不同直接分裂身份。

### 代码职责

检查返回成员 ID 合法、比较对象明确、无重复覆盖或无依据跨类型折叠；不通过相似分数自动确认语义 identity。临时分组尚不提交 canonical 映射。

### 输出与进入条件

输出拟同义组及必须保留的身份区别，附简短依据。同一身份即使定义竞争也继续进入步骤 4，不能为了避免 conflict 改判 different。新证据确实改变所指解释时才返回修订。

## 7. 步骤 4：解释内容与结构差异

### 输入

拟同义组、不同但相关的节点、关系契约与来源。

### 7.1 节点内容分析

1. 提取共同含义及可共同保留的内容。
2. 按语义列出实质差异，不列无意义的 JSON 文本差异。
3. 对每项差异解释原因：请求参数、固定定义、适用情形、实现方式、竞争口径或抽取错误。
4. 给出处理结论：统一、补充、条件化、竞争、修正；若差异确实改变身份，返回步骤 3 作分离判断。
5. 检查多项结论能否组合成完整一致的定义。

| 处理 | 必须成立的判断 | 输出责任 |
|---|---|---|
| 统一 | 同身份下等义表达，或不同实现均满足同一义务且不引入不同承诺 | 保留完整可复用含义，可保留必要 SQL pattern |
| 补充 | 同身份的信息能够共同成立 | 合并该身份的不同方面，不合并独立 Rule 义务 |
| 条件化 | 有语义相关且使用时可识别的条件解释差异 | 将条件与对应行为写入真实内容，处理重叠，不造默认 else |
| 竞争 | 可比较条件下有来源支持的要求不能共同满足，不能合理条件化，也非明确错误 | 同 identity 保留完整竞争定义 |
| 修正 | 抽取内容被来源或明确契约反驳 | 修正并记录依据；不继续把错误当业务口径 |

### 7.2 条件化检查

- 条件与行为差异有解释关系，不只是共现。
- 条件可从请求、输入结构或已知业务/数据语义判断，不依赖“选了哪个实现”。
- 每个已处理来源能够落入适合的分支；分支重叠时行为相容或存在有据优先规则。
- 条件、动作、依赖共同进入最终定义；未覆盖情况不凭空补 else。
- 固有业务值与请求变量分开，不能为提高泛化删掉定义含义。

例：县不同不能解释 COUNT/COUNT DISTINCT；实体唯一性和 JOIN 重复可能解释。若不同请求分别计数实体和记录，则返回 identity 分离。

### 7.3 真冲突检查

1. 对齐身份/关系角色、范围、条件与量词。
2. 明确各来源分别要求或允许什么。
3. 排除等价、互补和合理条件解释。
4. 检查是否有明确抽取错误可修正。
5. 剩余要求不能共同满足时保留竞争。

两个 SQL 输出不同不充分。例如请求允许任取一个并列第一，不同 tie-break 可都满足要求。当前数据上输出相同也不充分证明等价。可构造满足数据库约束的假设输入测试行为，但不能把它当作源数据库事实。

### 7.4 关系与结构分析

1. 对齐谓词的业务角色与方向；不同名字可同义，同名可不同义。
2. 结合节点判断边是否重复、互补、条件化、竞争或错误。
3. 层级需满足同范围的类别包含，多个父类可能合法；不强制统一层级深度。
4. 对不同结构问：各自表达什么？哪些意义相同或有差异？整合后分别在哪里承载？
5. 仅删除重复或在一致分支中可证明推导的冗余断言；不按节点数、边数最少优化。
6. relation_metadata 保留具体成员和声明强度，不能将若干组直接 union 后扩大互斥、共属或覆盖结论。

### 分工与输出

Agent 解释身份之外的差异；代码可提供字段 diff、重映射后的精确重复、路径见证、引用目录与查询结果。代码不判断业务兼容性，也不把自然语言解析成完备公理系统。

输出沿用精简 analysis：shared；differences 中的 difference、explanation、supporting_refs/evidence_ids、可选 applies_when、treatment。一个组可以有多类差异，不给整个组只打一个标签。

## 8. 步骤 5：构造完整局部提案

### 执行

1. 按身份结论复用或申请 canonical ID；尚不更新正式映射。
2. 为同身份构造一个完整整合定义，或完整竞争候选；不能逐字段交叉拼接。
3. 保持 Concept/Metric 的 NL 最小化、Rule 的 action 最小化；独立义务保留独立节点。
4. 显式创建/更新/删除业务边和必要契约，不靠 refs 推断全部关系；Metric.expression.refs 仍保留并正确重映射。
5. 同步关系组、分支边和受影响消费者；只有正确的语义关系才能替代绑定，不能为过唯一性校验随意删边。
6. 每个实质差异增加 result_refs，说明 treatment 落在哪些节点/边。修正项说明依据，不能无声丢失。

### 来源与身份映射

真正同义合并采用多对一 identity 映射；来源可以一对多支持输出。例如一个被错误抽成复合 Rule 的来源可由两个原子 Rule 共同保留。拆分必须逐项改写消费者，不能用一个 old→new ID 猜测所有引用。

### 局部范围

- Read-set：用于解释当前问题的定义与证据。
- Write-set：本次实际修改的节点、边、契约。
- Impact-set：代码枚举的引用、消费者与关系组。

只读不意味着必须修改；代码检查全部引用不意味着 Agent 阅读全部邻域正文。若提案需要扩大 write-set，先补必要读取与影响检查，再提交。

### 分工与输出

Agent 产出语义修改；代码分配临时 ID、解析 result_refs、编译标准 GraphManager 操作并计算影响。输出是完整可预览的局部图变化，不是自由文本建议。

## 9. 步骤 6：预览与独立审查

### 代码先检查

- 字段、类型、端点、引用及 relation_metadata 结构。
- 同数据库及代码可判断分支范围内 Concept 直接绑定唯一性；隐含业务范围由语义审查判断，不可自造 scope 绕过。
- 公式 refs 与表达式的一致性、完整候选、分支可用性。
- 仅对契约明确禁止环的子图检查循环，不要求业务全图 DAG。
- 删除、合并、改义涉及的反向引用已列明；原子依赖无遗漏。
- 提案依赖的工具内容不是 missing、too_large 或未完成的必要分页。

### Assessment 三层

1. **解释成立**：业务 identity 判定是否正确；是否把实现冲突当不同 identity；差异原因、条件化、竞争、纠错是否成立。
2. **解释落实**：treatment 是否进入实际节点/边；条件、动作、公式、角色和依赖是否完整；是否拼出无依据的新组合。
3. **修改保义**：来源支持的要求能否由结果重建；是否错误提升为无条件事实；受影响消费者和分支是否保持正确。

Assessment 读取原始来源及当前提案，不以 Merge Agent 的解释作为事实。它可以要求具体补读、修订解释或修改输出。源行为检查覆盖被处理的知识，不要求补全所有可能未抽取的知识。

### 通过条件与反馈

通过必须同时满足结构可提交、必要读取完成、语义审查认可及修改影响已处理。Agent 自报 DecisionReady 不足。

结构错误反馈到提案；来源/定义不足回读取；身份反证回步骤 3；条件或组合不成立回步骤 4/5。反馈指定出错对象与原因，避免泛泛“再优化”。同一任务内部允许有限修订，签名去重不能阻止基于反馈的修订。

SQL 回放按行为影响触发，不对每次 alias 合并都运行；执行一致只是证据之一，不证明普遍语义等价。

## 10. 步骤 7：提交、传播与重新检索

### 提交

代码在相同 base revision 上原子提交节点、边与契约变更；成功后才更新 canonical、edge、predicate 映射与来源对应。失败不污染正式索引或替换输入。

### 两种影响分别处理

1. 机械 ID 替换：前提是身份/关系同义已经审查通过，代码完成全量引用替换和结构检查。
2. 可能改变语义的字段/关系修改：检查直接消费者；消费者也需改动则继续传播，不需改动须经审查确认后停止该分支。不得仅凭 Merge Agent 自报无影响。

与当前事务不可分割的消费者/关系组修改必须在提交前完成；可以独立处理的新匹配任务提交后入队。不能先发布已知损坏的消费者，再期待下一轮修好。

### 候选刷新

每批完成提交后，对本批 seeds 与本轮修改的 canonical 重新执行候选检索。候选 IDs、相关定义/契约/证据签名改变才重新调用模型，避免遗漏 alias 导致的非邻居新候选。普通 top-k 不承诺全局无漏匹配。

### 正常结束

本批全部内容都有明确整合、独立保留、条件化、竞争或有据修正结果；已知硬约束处理完成；刷新没有新的相关任务。原始输入及来源仍可追溯。

没有正常 U/uncertain 出口。调用/迭代预算用于限制执行；耗尽而未完成则报运行未完成，不强制任选一个身份，也不报告完整成功。

## 11. 关系冲突的图内表示：本轮明确待 review 的扩展

主流程不应靠暂存纯关系竞争实现“成功”。现有 node alternatives 无法一般性表达只有边内容不同的真实竞争，因此建议以下有限边界：

1. 竞争确实属于同一个节点的真实定义时，沿用现有 node alternatives 与分支边。
2. 对**端点和业务关系已对齐、仅边的描述/限制存在真实竞争**，建议复用 compact alternatives 的思想支持边级内容候选：公共部分 + 完整差异覆盖 + 来源 + 冲突点。消费者必须明确选择候选，不得把全部候选当普通同时成立的边。
3. 该建议需要保存—读取—选择—重映射—关系组引用的最小往返试验；不能只证明 JSON 能存下来。
4. 不通过改变端点/谓词来伪装内容候选，也不为复用 node 容器捏造节点字段差异。
5. 多个不同 identity/多条边之间有关联选择的任意子图竞争不由单边候选自动解决。当前尚未设计其通用表示，不能声称该能力已完整支持；这类输入若无法按真实所属节点表达，运行不能被算作完成。

本节是推荐的新增表示方向，尚未得到用户确认或实现。它使节点/单关系内容竞争的处理路径明确，但不掩盖更一般子图关联选择的边界。除此之外，不新增 Constraint、通用分支引擎或 ontology 工作流节点。

## 12. 决策记录与工具的最小集合

运行时提案沿用并扩展现有结构：

```text
identity：成员、共同所指、保留的身份区别及依据
shared：共同内容
differences：difference / explanation / supporting_refs / evidence_ids
             applies_when? / treatment / result_refs
proposal：节点、边与契约操作，必要完整候选
```

不要求每个不变字段都写一份分析。对重要差异解释提供实际输出对应，避免分析正确而图丢条件。

工具保持少量：

- find_candidates：统一的端点/文本/邻域检索和分页，不按每类节点建独立服务。
- read_nodes：完整正文与关系摘要/分页分离，支持节点/关系组/契约的必要读取。
- read_evidence：按来源读取，保留完整性状态。
- 必要时复用受当前数据库范围约束的只读查询能力；不得要求模型验证没有工具或证据支持的键、重复和 NULL 事实。

preview/commit 是控制器职责，不把任意全图写权限暴露给 Agent。类型规则按需加载，operation registry 仅在 Rule 判断需要时提供一份。以实际读取记录去重，不重复注入全量图或指南。

## 13. 贯穿 mock：同义计数义务的不同实现

输入：

- R1：对请求指定的实体计数，使用 COUNT(id)；源查询直接读实体表，id 为唯一非空键。
- R2：对同一类请求实体计数，使用 COUNT(DISTINCT id)；源查询先与明细一对多 JOIN。
- 两个来源的县/年份过滤值也不同。

执行：

1. 代码根据 action/intent、输入及关系召回 R1/R2，提供来源。
2. Agent 读取对象角色与必要粒度证据，确认同一独立生成义务；不因 COUNT 语法不同分成两个 identity。
3. 差异分析发现输入是否出现重复实体可以解释实现差异；县/年份不能解释。
4. 构造原子 Rule：按实体身份计数；输入已经一实体一行时可直接计数，可能重复时须去重；保留匹配的 SQL pattern 和必要非空限制，不复制具体县/年份。
5. Assessment 检查条件是否成立、NULL 情况是否被忽略、实际 action 是否写入条件，且没有把 unrelated filtering/grouping 打包。
6. 代码检查 refs、applies_to、消费者与映射，原子发布。
7. 依赖该 Rule 的内容若只发生 canonical ID 替换，则机械更新；行为解释发生变化的消费者需检查。候选刷新可发现其他同义实现。

反例：若源请求分别计数实体和明细记录，则 identity 不同。若来源明确是同一义务、同一条件下不同政策，则留在同 identity 的内容阶段处理竞争。若两个实现都满足“任取一个合法结果”的义务，输出不同不构成冲突。

## 14. 实施与验证顺序

1. 先同步 identity、内容分析、Assessment 的语义边界及新节点/关系契约；修正 Event 绕过语义整合、业务边误作调度依赖、同名本地契约提前冲突。
2. 补读取摘要/分页和候选接口，保证所需证据可获取。
3. 扩展局部提案、分析到输出的对应、来源一对多和标准事务编译。
4. 用单关系竞争做最小表示试验，完成本节待 review 决策。
5. 加入批次候选刷新、影响分类、有限重试与恢复。
6. 用受控 mock 再用真实 case 图比较现有 baseline，记录身份精度、冲突判断、语义保留、SQL 回归与调用成本。

需要覆盖的反例：同关系多个不同目标、循环自证、同身份竞争实现、独立义务互补、比例字段交叉拼接、伪条件化、允许多种输出、高连接度 hub、新 alias 新候选、来源一对多重构及纯边竞争。

设计主张与证据状态：上述机制定义了职责和可检查决策；它们是否降低错误合并、提升结构整合质量、控制 LLM 成本，均需实验。没有全局最优、完备一致性或输入顺序完全不影响语义结果的保证。
