# Ontology graph merge：完整修改方案

更新日期：2026-11-07。本文汇总设计；v60–v63 保留讨论历史。实现采用显式的 identity 阶段，不能将 identity 隐含在通用提案中。代码改造与实验状态见 [v64 实施记录](ontology-merge-v64-implementation.md)；本地测试通过不代表真实模型合并已通过。

## 1. 目标与范围

将多个 case graph 中的业务知识整合到全局图：对齐同一 identity，整合兼容内容与合理结构，修正有据错误，保留真实竞争，并维护原始知识到结果的对应。

正常知识输出只有整合图 G*；ID 映射、结构重写对应、来源与 checkpoint 是管理记录，不设置正常 U，也不以 uncertain 作为默认退出。执行错误、必要工具不可用、预算耗尽不等于成功；不通过强制合并或静默丢弃输入伪装完成。

保留 Concept、Metric、GenerationRule、Event 的现有要求；Concept/Metric 保持 NL 最小化，Rule 保持 action 最小化。语义边显式生成，Metric.expression.refs 保留。不更新 metadata store，不发明 Constraint、通用图推理器或更多运行 Agent。

## 2. 核心语义规则

### 2.1 Identity 与内容差异分开

**只有差异改变业务所指或独立生成义务，才判不同 identity，不能同义合并。**

同一 identity 的描述、绑定实现、计算实现或业务口径差异，留到内容整合中处理；不能因难以统一而拆 identity 来避开冲突。内容分析出现新的身份反证时可以纠正分组，但必须说明实际业务含义如何不同。

名字、物理端点、公式、operation intent 和相同邻居都是证据，不是单独充分条件。关系判断使用方向、业务角色、相邻对象与范围；相同关系可以有多个不同目标，不默认函数性。缺边不是否定，待确认对应不能循环自证。

### 2.2 内容与结构只判断必要问题

不要求给每项差异填写分类标签，但必须按以下标准处理实际差异：

| 情况 | 判断与处理 |
|---|---|
| 同义表达、满足同一义务的实现选择 | 统一完整含义；具体 SQL 写法不同不自动成为冲突 |
| 同身份互补信息 | 整合内容；不同独立义务仍保留不同节点 |
| 条件解释不同实现 | 条件须与行为有关、使用时可识别，并落实到实际定义；检查分支重叠，不虚构 else |
| 真竞争 | 同身份/关系角色及可比较条件下，来源支持的要求不能共同满足，且不能合理条件化或有据纠错；保存完整候选 |
| 抽取错误 | 来源或明确契约能反驳该抽取时修正；保留原始证据和理由，不继续当业务政策 |
| 层级、谓词或分解不同 | 先解释各自含义，再联合改节点/边；不强求唯一层级，不因多个父类就判冲突 |

分析可逐项进行，结果必须是完整一致的定义。分子/分母/总体/单位/依赖、condition/action/作用对象不能交叉拼成无依据的新组合。

条件与行为共现不等于解释。例如不同县的 COUNT/DISTINCT 差异应检查输入粒度，而不是按县选择。不同 SQL 输出也不等于冲突：请求允许任取并列第一时，不同合法选择可能都正确。

图冗余只处理重复断言和在同范围、一致分支与已知契约下确实可推导的断言；不追求最少节点。不删除承载未另行保留的限定、组知识或消费者要求的元素。

## 3. 最小运行框架

一个 Merge Agent，一个独立 Assessment，外加确定性控制器。

```text
准备上下文
    ↓
Merge Agent 显式 identity 判断
    ↓
Merge Agent 内容整合与结构修改提案
    ↓
代码预览 + 独立 Assessment
    ↓
原子提交 + 索引/任务刷新
```

读取不足就补读；解释或提案有误就有限修订；提交产生相关新信息再重新检索。内部控制步骤不变成更多 Agent，也不要求模型输出独立 DecisionReady、六类差异标签或完整推理过程。

## 4. 图与对应关系的组织

### 4.1 三种视图

- **原始输入**：每个 case graph 及证据不可变，用 `(source_graph_id, local_id)` 定位。
- **Working graph**：已经整合并通过审查的图，具有 revision。
- **Candidate preview**：在 working copy 上应用本次提案；未通过时不影响 working graph。

incoming 内容独立可读，不先把所有 case 图无条件并入正式图。否则临时重复绑定或契约冲突会被当作已接受事实。

### 4.2 可安全替换引用的映射

保留单值 node/edge mappings，用于真正可替换引用的情形：

```text
caseA.school ─┐
              ├→ global.school
caseB.school ─┘
```

节点同义经审查后，代码统一引用。边在端点、谓词、范围、分支及断言含义一致时可归并。只看 triple 不足。代码可自动归并确定性重映射后相同的事实，其他语义归并由 Agent 提案并经审查。

新增且原样保留的对象由代码自动产生来源 ID 对应。canonical 含 alternatives 时保留分支对应，不把旧版本静默指向默认候选。

### 4.3 结构重写对应

一个旧节点/边可由多个新节点/边共同表达。此时不能把单值映射改成列表后用于自动替换；需记录结构对应：

```json
{
  "before": ["caseA:e1"],
  "after": ["new:e1", "new:e2"],
  "explanation": "该原始类别包含关系由这条同范围的 is_a 路径表达。"
}
```

before/after 可以各含多个节点或边；代码生成和解析带类型/来源的 handle。before 锚定原始输入或提交前 revision，after 锚定候选/提交后 revision。涉及候选时指明 alternative，不混用互斥分支作为共同见证。

该记录表示旧知识如何被新结构承载，不表示各元素逐个同义，也不自动赋予路径推理能力。新图可增加其他来源支持的信息，因此不要求两边整个子图完全等价。若是纠错，明确指出修正和依据；有据删除时 after 可为空。

即使 before/after 各只有一个元素，也不能据此自动认定可替换引用，所指或类型可能已被修正。

### 4.4 来源与对应不能混淆

Identity 多对一、来源支持一对多、结构表达多对多是不同事情。

例如原边 `C is_a A` 被路径 `C is_a B; B is_a A` 保留，原边自身并不证明两个中间断言。新路径的独立来源必须确实支持各断言，不能将旧来源按 before×after 自动传播。

结构记录用于审计、验证和明确迁移，不是在线系统的新隐式业务规则。在线消费整合后的真实图。历史记录保留前后 revision，不在每次提交时生成全历史巨大映射矩阵。

## 5. Agent 的最小提案

```text
identity_groups:
  members + meaning

edits:
  标准节点、边、契约操作；必要的完整竞争候选

changes:
  before + after + explanation（仅实质变化）
```

- identity_groups：同一业务身份的成员及一句共同含义。不同身份的必要区分可在变化解释中说明，不写全候选辩论记录。
- edits：实际图修改，沿用 GraphManager 操作形态，不再造一套图 DSL。Agent 使用已提供 handle 和临时新 ID，代码负责最终命名。
- changes：合并原 differences 的实质解释与 result_refs。说明为什么变化、条件化/竞争/纠错的依据，以及原意在哪里保留。证据引用来自已提供的有效来源；条件必须进入实际 edits，不能只留在解释。

不变对象、原样插入、纯机械替换、确定性重复归并的管理记录由代码生成。仅对真实内容/结构变化、竞争或删除增加解释。自动记录存在不等于语义覆盖通过。

## 6. 第一步：准备上下文

### 代码执行

1. 保留来源限定的节点/边/谓词 handle，按数据库真实身份对齐物理端点。Value 保留所属列、类型和值，不采用默认 SHA-256。
2. 本地同名契约先保留来源区别，避免语义比较前拒绝；root 契约不可重定义。
3. 将本批全部语义节点、显式边和本地谓词列为处理对象，包含 edge-only/predicate-only 更新。
4. 使用名称/定义/行为、物理输入和关系角色召回候选；本批尚未提交内容也可参与候选。
5. 对 Concept 直接绑定争用完整枚举 mandatory 比较项，其他候选 bounded top-k。
6. 提供必要定义、边摘要、契约和来源目录；记录实际读取与分页完整性。

### Agent 执行

可请求补读，但只需简短说明“需要什么、为了区分什么或检查什么影响”。读取邻居不自动读取其所有邻居；相同关系/邻居不是身份证明。

### 边界

实际裁决的候选、引用其业务含义的依赖、用于论证的契约与来源要完整可读；修改 relation_metadata 时读取完整该组。代码完整掌握反向引用目录，不将所有消费者正文都塞进 prompt。

该阶段输出可分析上下文，不要求预先穷尽所有 soft 候选或全库语义知识。

## 7. 第二、三步：显式 identity 判断与整合提案

这两项是独立的模型调用，前一步的结构化 identity groups/distinctions 交给后一步；可以复用同一模型，不增加独立的业务 Agent。内容阶段发现真正的业务身份反证时返回 identity 阶段。不能用实现/口径不一致作为拆分 identity 的理由。

### Agent 执行

1. 确认哪些节点同一业务 identity。不能按实现/口径差异直接分裂身份，也不能删除限定、提升到共同父类制造同义。
2. 对实质内容差异建立解释，按照第 2 节判断是否统一、补充、条件化、竞争或修正，不要求强制分类标签。
3. 联合解释相关谓词、层级和关系组；提出节点与边的实际修改。
4. 构造完整节点定义与必要候选，不逐字段自由组合；保留各节点最小化。
5. 对结构变化或删除填写 changes，标明前后对应及理由。

### 代码支持

提供按需读取、候选分页、类型及关系契约、反向引用目录。遇拟修改超出已有范围时补上下文，而不是把任意全图写权限交给模型。

### 输出

一个 identity_groups + edits + changes 提案，尚未更新 canonical、正式图或映射。

## 8. 第四步：代码编译、预览与独立审查

### 8.1 代码编译顺序

1. 解析来源/临时 handle，拒绝不存在或越界的对象。
2. 按拟同义组确定稳定 survivor 和临时映射，准备新对象 ID。
3. 只在 schema 声明的引用槽位替换节点 ID；不全局替换 description/SQL 字符串。
4. 将显式 edits 应用于 working copy。新增节点及其边可同事务建立，不能因业务环要求逐节点拓扑调度。
5. 对确定性相同的边归并，产生安全的单值 edge alias；其他边修改按受审提案执行。
6. 同步 changes、分支引用及 relation_metadata 中安全的单值替换。旧边变路径/旧节点拆分时不能机械扩成列表。
7. 用反向索引找到所有删除、拆分、改义及契约修改的使用位置。除同义替换外，要求提案显式处理，不猜消费者目标。
8. 检查字段/端点/引用、Concept 直接绑定唯一性、分支与关系组结构及明确禁止的循环。无效边返回反馈，不静默 drop。

代码可验证存在性、结构与已声明规则，但不能凭 after 非空判定原意已保留。

### 8.2 Assessment 的三个检查项

**决定正确：**identity、差异解释、条件化/竞争/纠错有依据；同身份实现差异没有被当成不同身份；完整定义保持原子性和组合一致性。

**候选质量：**检查实际候选内的 incoming 语义内容与受影响已有知识，包括未被 edits 修改的节点/关系。节点最小化、Rule 的决策范围、业务关系、证据强度均须符合规范。来源 extraction 状态不能替代检查；该结论独立于 identity 与保义。

**修改保义：**对照原始证据、changes 和实际 preview，受支持的原意与消费者仍成立，条件/依赖未丢失，没有新增无依据限制；纠错有据，不强求保留抽取错误。

只检查本次实际处理或影响的知识，不评估所有潜在遗漏。可以使用符合约束、明确标为 hypothetical 的区分性输入检查解释，但不能当成源数据事实。

### 8.3 修改反馈与停止

缺信息给出具体补读；身份反证返回身份判断；解释错误修订解释；解释正确但图未落实则修订 edits。使用一个有界反馈循环，不设置多套 Agent。

可提交要求：必要读取及已知 mandatory 项完成、结构有效、影响已处理、Assessment 通过。Merge Agent 无需提交 DecisionReady。

SQL 回放按实际计算/生成行为影响触发，纯 alias 合并不必重跑；单快照一致不能代替语义审查。

## 9. 第五步：提交与增量刷新

1. 在相同 base revision 原子提交图、必要消费者修改、映射、changes 与来源记录；失败均不更新。
2. 更新检索与引用索引。已确认同义的纯引用替换由代码完成结构检查。
3. 实际含义变化检查直接消费者；消费者需改动则继续传播，经审查确认不受影响则停止该分支。不能先提交已知损坏消费者再等后续修复。
4. 每批对本批 seeds 和改变的 canonical 刷新候选，发现由新 alias 等引入的非邻居候选；只有相关候选/内容/契约/证据签名变化才再调用模型。
5. 本批内容有合法处理结果、已知硬约束处理完成且无新的相关任务时结束。普通 top-k 不证明全局无漏配。

不为局部性展开整个无向连通分量；也不承诺所有任务都很小。高连接度对象可能有很多引用，但代码枚举引用与 Agent 读取全部正文是不同事情。

## 10. 非一对一对应实例

### A. 同义节点及重复边：代码自动重映射

两个 School 经判断同 identity，合并到 G.school。代码更新边端点、targets/表达式中的声明引用，并归并真正相同的边。Agent 不逐条填写机械映射。相同端点不同角色的边保留区别。

### B. 一条旧边由路径承载：Agent 说明组合含义

```text
图 A：C is_a A                         eA
图 B：C is_a B；B is_a A              eB1, eB2
```

假设 B 的两个断言有依据且同范围，契约允许相应推导。可保留路径，记录 eA -> {G.e1,G.e2} 共同承载。不能把 eA 映射到路径的任一单边；不能把图 A 来源当成两个中间断言各自的支持。

若关系组引用 eA，必须重新审查组含义；路径两条边未必同 owner，不能机械替换成员。无法保义时重新设计修改，不为简化强行丢组信息。

### C. 复合 Rule 拆分：Agent 显式改消费者

一个旧 Rule 包含两个独立义务，可由 R1、R2 共同保留。记录 old.R -> {R1,R2} 的结构对应，不建立 old.R -> R1 的同义 alias。

代码列出每个消费者引用位置；Agent 按角色明确改为 R1、R2 或合法组合。单值 ref 不能自动变列表；来源可支持多个输出，不能强制每个输入只有一个 canonical。

## 11. 关系冲突表示：唯一仍需单独确认的存储扩展

changes 表示修改对应，不是冲突存储。两个互相矛盾的普通边不会因有 changes 而合法共存。

建议采用有限方案：

- 真实竞争属于节点定义时，继续使用 node alternatives 与分支边。
- 端点、业务角色及范围已对齐，仅关系内容有竞争时，建议复用 compact alternatives 思路到边内容，保留完整候选、来源和冲突点；不能通过伪造节点字段差异规避。
- 最小试验必须覆盖保存、读取、选择、重映射与 relation_metadata，不仅是 JSON 可序列化。

边级内容候选是待 review 的新设计，不是已有能力。任意跨多节点/多边关联选择也不由此自动解决。若当前表示无法承载必要竞争，不能宣称该输入已完成整合；不引入正常 U 来掩盖该边界。

## 12. 代码修改清单

| 模块 | 拟修改 |
|---|---|
| `application/merge_graph.py` | 保留安全单值映射，增加结构对应；不要求每个输入都有唯一 canonical |
| `capabilities/graph_merge/models.py`、`reconciliation/models.py` | 精简提案为 identity_groups/edits/changes；支持多节点、来源一对多与明确分支 |
| `identity.py` | 保留候选检索能力，补物理 owner/关系信号；业务 identity 由 Merge Agent 结合上下文判断，不一次锁死所有组 |
| `operator.py`、`workflow/run.py`、`workflow/group.py` | 四步循环、局部 batch、影响处理及批次候选刷新；复用 checkpoint/有界重试 |
| `transactions.py` | 从单 group preview 扩展为局部操作 batch，复用 GraphManager revision/原子提交 |
| `edges.py`、`references.py`、`relation_metadata.py` | 仅安全映射自动化；复杂对应显式改写；无效边不能静默丢失 |
| `llm/agents.py`、`llm/tools.py`、`bootstrap/graph_merge.py` | 一个 Merge Agent + 独立 Assessment；整合原身份语义调用，读取摘要/分页/候选入口与必要只读 DB 证据 |
| `reconciliation/service.py`、`validation.py` | Event 纳入语义路径；去掉“每来源恰好一个 candidate”和常规保守 fallback；保留真实竞争与完整候选验证 |
| merge prompts | 同步当前 schema、精简 Markdown、统一 identity/内容边界与三项 Assessment；消除旧 target.sql_expression 指引 |
| `schema/relation_contracts.py` 与导入边界 | root 不变；case-local 同名契约先来源隔离再语义处理，不直接放宽全局重定义限制 |
| 报告/调用方与相关测试 | 更新映射数量≠知识覆盖的假设，展示结构重写而非伪造单值映射；新旧 checkpoint 明确版本边界 |

现有文件划分可继续复用，不要求增加同等数量的新模块。跨类型纠错属于明确重写，不作为无审查 alias。

## 13. Prompt 与工具的精简要求

Merge prompt 只包含任务、核心判断边界、三个输出块及工具导航。类型/关系规范按需读取；operation registry 只在 Rule 内容判断需要时提供一份，不重复全量注入。

Assessment prompt 只包含“决定正确、候选质量、修改保义”、原图和实际候选、改写解释、证据入口与代码发现的影响。三个检查项由一次独立评估完成，避免质量检查被 identity 分析遮蔽；不增加 Agent 或工作流阶段。实际候选已提供，因此不重复注入 edit bodies。结构错误由代码返回，不让模型反复手查 JSON schema。

复用少量入口：候选检索、节点正文与关系摘要/分页、来源证据读取、必要时受当前数据库限制的只读查询。不能要求模型核实未提供的键、NULL 或重复性，也不把 DB 探索变成所有任务的强制前置步骤。

## 14. 实施顺序与验收

### 阶段 A：先验证提案和映射协议

用确定性 fixture 验证同义多对一、边到路径、Rule 拆分、来源/分支对应、关系组引用与原子回滚。代码能检查引用和事务；语义保留预期由人工 fixture 给定，不能宣称代码证明语义等价。

### 阶段 B：连接精简 Agent 与 Assessment

用少量 mock 验证身份与内容边界、条件化和组合正确性、按需读取与分析落实。不先批量跑全库。

### 阶段 C：真实 case 图与现有 baseline 比较

选择已有 school cases 及一个有计算/Rule 差异的组。查看完整来源、提案、preview、Assessment 和结果，检查 NL2SQL 行为及成本。此处是计划，不是已执行结果。

| 必测场景 | 验收重点 |
|---|---|
| 同身份不同公式/口径 | 不因内容竞争拆身份 |
| 同关系多个对象 | 不默认函数性，不强合并 |
| COUNT/DISTINCT 与无关县值共现 | 以粒度解释，不伪条件化 |
| 任取并列第一的不同实现 | 不因输出不同就造冲突 |
| 两套分子分母 | 不交叉拼接无依据公式 |
| 一条边变路径 | 共同表达正确，来源不错误传播 |
| 复合 Rule 拆分 | 来源一对多、消费者显式改写 |
| relation_metadata 引用被重写边 | 不机械扩列表或静默丢组声明 |
| 高连接度节点 | 分页可读，问题相关范围内推理 |
| 新 alias 产生非邻居候选 | 刷新能发现，不全图重复推理 |
| preview/commit 失败与恢复 | 图、映射、记录一致，不部分污染 |
| 纯关系内容竞争 | 经确认的图内表示可保存、读取和选择 |

验收不仅看图是否合法，还看错误合并、信息丢失、来源要求保持、真实竞争保存，以及调用/token/时间。算法有效性、规模收益和创新性仍需实验，不由本设计文档证明。
