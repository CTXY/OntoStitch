# value_concepts：同一列下的多个取值 Concept

## 触发与理想状态
- **触发条件**：按 DimensionValue.column_ref 聚合 Concept→Value 的直接 grounded_on，涉及多个值及多个 Concept 时触发；不证明一一对应、互斥或值域完整。
- **健康状态**：区分属性维度、属性取值与具有该属性的对象总体。多个健康取值 Concept 可分别保留，无需共同父节点。

## 核查材料与示例
- **节点与物理归属**：核实 Column 身份、受治理 Value 记录与 value_of，读取各 Concept 完整定义/匹配组及相关分支。
- **完整性与证据**：掌握相关完整 Concept→Value 绑定及已有类别/维度关系；若主张覆盖/互斥，须额外有完整值域或业务约束，不把一页 profile 当全域。
- **健康示例**：Female→F、Male→M，各 Value 属于 SEX 列，不强建 Sex 父类。
- **有据层级示例**：FemalePatient 明确是患者总体且具 F 条件，才可讨论其 is_a Patient。
- **错误示例**：看到 F/M 就宣称二元穷尽；把两条直接边都改绑 SEX Column，既丢条件又造竞争。

## Writer 判断与调整步骤
1. **辨别指代层次**：比较实际指代层次与条件，相同标签不同列不默认同义；属性维度不是取值的天然集合超类。
2. **核实包含关系**：仅有同类对象包含依据时使用 is_a；修复角色/归属错误时保留完整匹配和来源，物理目录本身只读。
3. **创建与身份边界**：新维度节点需独立业务依据和完整写契约，不造空壳父类；新关系按实际契约登记，身份判断交回 Identity。

## Assessment 核查要点
- **事实核验**：核对指代层次、完整匹配、Value/Column 归属及每项新增包含/覆盖/互斥主张。
- **保义与通过边界**：独立取值无共同父类可通过；不得以更简洁为由丢失分类条件或违反直接物理绑定政策。
