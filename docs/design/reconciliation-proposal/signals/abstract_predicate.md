# abstract_predicate：抽象谓词

## 触发与理想状态
- **触发条件**：实际边使用抽象谓词（当前为 `has_attribute`）时触发，通常表示只说明角色而不具体，尚未确定正确主体或目标谓词。
- **健康与例外状态**：健康边应使用准确具体谓词；`has_birth_date extends has_attribute` 的类型声明本身没有问题。旧抽象边若已退役且有保义后继，也可无需修改。
- **禁止掩盖**：当前存活边若确实违反禁止抽象谓词的写入约束，必须修复；证据不足时，不能用任意具体名称掩盖未知含义。

## 核查材料与示例
- **核查要点**：掌握两端类型、指代/定义及相关分支，原边的方向、说明、范围与来源，候选谓词契约，以及端点对上的完整相关边；仅在改变属性承载者时补充必要业务路径。
- **影响范围**：改边时核对引用它的 `Concept` metadata 和直接受影响消费者；角色不明时再读 `Question / Gold SQL`，不展开整个邻域。
- **可改示例**：`Patient → Birthday` 明确表示患者出生日期，且已有同义契约时，可使用 `has_birth_date`。
- **不可推断示例**：诊断存于 `Examination` 表，不足以把患者诊断关系改成检查记录诊断；**存储位置不决定业务归属**。

## Writer 判断与调整步骤
1. **确认现状**：沿当前映射确认边仍存活，核实是否确实为抽象谓词。
2. **判定属性与谓词**：根据节点含义、边说明及必要证据确定“谁的什么属性”；复用契约匹配的具体谓词，无合适契约时登记有据的新谓词。
3. **执行调整或标记**：
   - 仅在原主体/方向有据错误时修改端点；合并严格重复边时保留来源、分支及 `metadata` 引用。
   - 已是具体谓词或已有合法后继时，说明 `keep`。
   - 角色尚不明记 `needs_context`；涉及未确认身份合并记 `needs_identity`，**不用宽泛 `related_to` 替代**。

## Assessment 核查要点
- **问题与谓词**：确认实际存活边的问题、具体谓词契约及主体/方向有据。
- **保义与引用**：核对旧断言后继、来源、分支和引用。
- **通过边界**：具体谓词的继承声明不应被误报；仍有非法抽象边不能通过，**不能仅凭名称变具体就认可**。
