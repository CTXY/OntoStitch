# source_selection_variants：不同来源选择不同物理输入

## 触发与理想状态
- **触发条件**：检测器解析直接 SELECT 引用，与原 Concept targets 相交；映射到同一当前 Concept 后，至少两份来源选择集合不同即触发。
- **检测边界**：这是受限投影分析，不是全部 SQL 血缘；不涵盖所有 WHERE/JOIN/ORDER BY 用途。未投影不代表无效，不同投影不证明身份不同或知识冲突。
- **健康状态**：同一 Concept 可保留代码标识、名称显示等多种完整匹配；不因差异强建选择 Rule 或永久首选列。

## 核查材料与示例
- **当前与历史内容**：读当前完整 targets/target_expressions、定义与相关分支；按授权 source_snapshot_id 读各 variant 的**原节点完整匹配与角色**，不是当前摘要。
- **原始证据与消费者**：读这些来源的 Question、完整 Gold SQL 和必要 evidence；核实物理目录。涉及计数/选择兼容性时再补消费者的真实公式/行为与直接边。
- **健康示例**：School 的 code/name 分别承担标识与显示，保留两种匹配。
- **差异核查示例**：COUNT(name) 与 COUNT(id) 遇 NULL、重复或粒度差异可能不同，不可默认互换。
- **错误示例**：本轮只投影 name，就将 School 改名 SchoolName 并删 code 匹配。

## Writer 判断与调整步骤
1. **还原选择角色**：确认归档来源到当前节点的映射，逐来源解释显示、标识、计数等有据角色。
2. **保留或修复**：相容且已表达清楚时 keep；必要时澄清角色或修复确实丢失的匹配条件/关系，不能把独立外层组拼成联合键。
3. **泛化边界**：条件化/参数化须有可识别条件、合法 schema 和兼容消费者，不写“按上下文任选”掩盖固定口径冲突。
4. **内容与身份边界**：需重做身份/节点整合时明确移交；不凭一次 SQL 建全局策略，不凭不同源表推断 JOIN 许可。

## Assessment 核查要点
- **事实核验**：逐来源验证完整匹配、选择角色、当前表示及消费者，检查条件和来源去向。
- **保义与通过边界**：相容差异无需新 Rule；SQL 投影不能成为删除知识、设永久偏好或宣布计数等价的依据。
