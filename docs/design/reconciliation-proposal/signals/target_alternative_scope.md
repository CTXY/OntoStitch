# target_alternative_scope：终点版本义务

## 触发与理想状态
- **触发义务**：关系原来依赖的终点版本被重写或映射为多个 alternatives，controller 无法证明安全继承时触发；同 ID 不代表含义未变。
- **健康状态**：只有原命题在所有相关终点版本都成立，或有明确合法后继保留其知识及消费者行为，才能保持共同关系。

## 核查材料与示例
- **完整新旧版本**：读原目标完整版本、当前相关完整 alternatives/conflict_points 与真实映射；补齐受影响起点的决定性字段/分支。
- **影响集合**：取得 controller 计算的**完整受影响入边/消费者集合**、原边和后继的说明/范围/来源；不是无差别读取目标全部邻域。
- **健康示例**：School 的不同匹配版本均支持原 Student enrolled_at School 关系。
- **错误示例**：利润率依赖含税销售额，却将销售额终点分支 ID 写进 depends_on.alternative_ids；该字段只选起点版本。

## Writer 判断与调整步骤
1. **还原原命题**：明确原关系依赖的目标含义，逐相关终点版本核查，不只核对名称与 ID。
2. **限定合法范围**：需耦合选择时只使用现有合法表示；可据实限制起点分支，但不能假装选中了终点。
3. **节点重写边界**：必须改变目标内容时走完整 node_rewrite，保留全部来源；不能任意普通化冲突或拆出独立身份方便接边。
4. **能力与身份边界**：现有契约无法表达必要终点约束时保持未接受状态、说明能力缺口；身份安排有反例则移交 Identity。不造 target_alternative_id，也不用描述文字冒充消费者支持。

## Assessment 核查要点
- **事实核验**：逐关系验证原目标含义、各终点版本、起点条件、来源与消费者；缺少合法必要版本约束就不能关闭义务。
- **保义与通过边界**：端点类型正确或 graph 编译成功，不证明版本范围正确。
