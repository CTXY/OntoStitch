# related_decisions：Rule 共享作用对象

## 触发与理想状态
- **触发条件**：至少两个 GenerationRule 通过 applies_to 共享语义操作数时触发；不证明同时触发、同一身份、行为等价或冲突。
- **健康状态**：独立决策与有据条件变体可共享对象；不能只因共同 intent/SQL 操作就合并，也不重新审计已接受 Rule 的原子性。

## 核查材料与示例
- **完整决策与关系**：读取相关 Rule 的 condition/action/reason/operation_intents/triggers 及相关完整分支，**每条 Rule 的全部 applies_to 出边**。
- **作用对象与粒度**：作用对象按类型读取：Metric 的公式/refs、粒度与直接输入；Concept 的定义、匹配组与条件。只在判断遗漏规则时补共享目标的完整 applies_to 入边。
- **健康示例**：患者去重与指标排名分别适用，关系准确，无需合并。
- **修复示例**：要求先按客户汇总再排名的 Rule，被错误重定向到订单行粒度。
- **不可裁决示例**：COUNT(*) 与 COUNT(DISTINCT patient_id) 的差异需对象与重复记录前提，不凭文本或来源数量投票。

## Writer 判断与调整步骤
1. **还原完整决策**：还原每个完整决策、条件与对象，triggers 命中不等于条件成立。
2. **修复关系**：只修复有据的 applies_to 端点、角色或范围问题，保持计算粒度、行为及条件；不将独立动作强制拼为共同动作。
3. **内容与身份边界**：同一身份的重新分组交回 Identity/节点整合；缺少计算相容性前提则说明缺失，不任意删 Rule 或编造 NULL/并列处理要求。

## Assessment 核查要点
- **事实核验**：逐 Rule 比较前后条件、行为、理由与全部作用对象，核对粒度、分支、消费者及来源。
- **保义与通过边界**：共享对象本身可健康；不能只确认公共目标仍存在就忽略其他操作数或行为回退。
