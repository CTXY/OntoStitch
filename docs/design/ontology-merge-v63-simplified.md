# Ontology merge v63：精简流程与结构重写对应（待 review）

> 完整修改方案已统一汇总到 [ontology-merge-implementation-plan.md](ontology-merge-implementation-plan.md)，包括执行流程、Agent/代码职责、映射与结构对应、代码修改清单和验收计划。本文保留精简设计的讨论依据。

日期：2026-11-07。本文是对 v62 的精简提案，重点明确 Agent 与代码如何协作修改图。未修改生产代码，未运行新的 merge 实验。

## 1. 保留什么，删减什么

核心只保留两项语义任务：确认业务 identity；解释同身份内容及相关图结构的差异。前者不能按实现/口径差异拆身份，后者仍需区分可整合内容、真实竞争和有据纠错。

将七个外显阶段压成四个：**准备上下文 → Agent 提案 → 验证/审查 → 提交与刷新**。代码内部仍有必要步骤，但不要求模型按多层状态机逐项作答。

精简方式：

| v62 中容易重复的内容 | v63 建议 |
|---|---|
| identity、shared、differences、treatment、result_refs 分别填写 | identity 组给一句共同含义；仅对实质变化记录 before/after/explanation，兼作差异说明和结果对应 |
| 每个差异必须在六种类型中分类 | 保留分类的判断准则，不要求每项填写分类标签 |
| 单独的 DecisionReady 输出 | 删除；由读取完整性、引用检查和独立 Assessment 控制能否提交 |
| 每次讨论完整推理闭包、所有可能循环 | 代码检查明确契约；Agent 只处理当前实际影响，不新增通用 reasoner |
| 每次为所有不变字段证明覆盖 | 自动保留未修改对象，仅解释实质变化、竞争与删除 |
| 多种扩展原因/影响标签 | 读请求只说明“需要什么、为了判断什么”；代码区分机械替换与其他修改 |
| 每个 soft 候选完整书面裁决 | 对实际合并组、必要区别和 mandatory 争用给理由；普通检索不要求全库穷尽证明 |

不能删的是：identity 与实现兼容性区分、条件化不得伪相关、完整定义不能交叉拼接、真实竞争不能当 ordinary facts 同时发布、变化涉及引用需原子处理。这些直接防止错误合并或知识丢失。

## 2. 当前映射接口的真实限制

`application/merge_graph.py` 中 CanonicalIdMapping 是 `input_id -> canonical_id`，分别用于 node_mappings 和 edge_mappings。`operator.finish_merge` 要求每个 incoming node 都有映射；`edges.normalize_edges` 在节点 ID 重映射之后按端点、谓词和属性归一化边。`transactions.preview_group` 仍围绕单 group 的节点替换生成预览。

因此当前能力接近：节点多对一、边重复归并。但不能忠实表达：

- 一个复合节点由多个新节点和关系共同重表达。
- 一条原始边由一段路径保留其含义。
- 多条原始边被一个更准确的局部结构替代。
- 一条错误断言被有据删除，而非映射到一个假目标。

把 canonical_id 改成 ID list 仍不够：列表无法表达目标是共同实现一个含义，还是可选择的几个版本，更不能告诉每个消费者应该引用哪一项。

## 3. 两种对应，分别处理

### A. 可替换引用的身份/断言映射

节点确认同 identity 后，代码维护 old_id -> canonical_id；多个 old_id 可以指向同一结果。相同事实的边归并也可有 old_edge -> canonical_edge，但必须保留适用范围、分支及断言含义。

映射只说明引用替换，不代表删除来源历史或把所有版本内容当成相同。替换到包含 alternatives 的 canonical 后，必须保留原有分支对应，不能静默指向某个默认版本。

结构对应恰好是一个 before、一个 after，也不能自动升级为这种 alias：类型/所指可能已被纠正，仍须明确判断该引用是否可替换。代码可自动确认重映射后完全相同的边；其他边的同义归并需要审查通过的具体提案。

新建且原样保留的对象由代码自动记录来源 ID 到新 ID 的对应。没有结构变化时，Agent 不需填写逐项对应表。

### B. 结构重写对应

结构变化时，保存一个小的变更记录：

```json
{
  "before": ["caseA:e1"],
  "after": ["edge.new_1", "edge.new_2"],
  "explanation": "原先的类别包含关系由这条同范围的 is_a 路径表达。"
}
```

before/after 可各有多个节点或边；元素类型和来源通过代码提供的 handle 解析，不让模型猜。before 绑定不可变输入或提交前 revision，after 绑定本次候选/提交后 revision，避免同一稳定 ID 的内容修改使审计失去意义。

这是来源知识到结果结构的对应记录，不是可执行 ontology 关系，也不是自动推理规则。它表示指定内容如何得到处理，不表示 before 和 after 的所有元素逐一同义。

区分以下情况：

- 保义重表达：after 的组合保留 before 的相关业务含义。
- 整合补充：after 还包含其他来源支持的新含义，不能声称两边全图完全等价。
- 有据纠错：explanation 指出错误和依据；删除时 after 可为空，但必须独立批准。

竞争候选必须指明具体 alternative，不能将多个互斥版本一起放在 after 并当作同时成立的见证。最小记录不解决任意子图竞争存储，v62 的表示边界仍保留。

## 4. Agent 的最小提案

```text
identity_groups:
  members + meaning

edits:
  标准节点/边/契约操作，必要的完整候选

changes:
  before + after + explanation（仅实质变化）
```

- identity_groups 指定哪些语义节点同身份，以及共同业务所指；canonical survivor 可由代码稳定选择。
- edits 是真正可执行的图修改。代码可向 Agent 暴露当前 GraphManager 的精简接口，不再生成第二套图 DSL。
- changes 合并原 differences 的实质解释与 result_refs，解释条件化/竞争/纠错，并记录结构去向；来源证据使用已有可核查引用，条件必须进入 edits 中实际节点内容。

普通保持不变、插入新节点、机械 ID 替换由代码生成记录；只有改变含义、重组结构、竞争或删除才需要额外说明。不能因为精简而省略重要差异。

本 proposal 仍使用临时/来源 handle。代码给新对象分配最终 ID，并重映射 edits 和 changes；映射在成功提交前不生效。

## 5. 四步执行流程

### 第一步：代码准备上下文

1. 保留原始图，提供来源限定 handle；物理端点按真实数据库身份对齐。
2. 用名称/内容、物理锚点和关系角色召回候选；已知 Concept 直接绑定争用全部纳入。
3. 提供候选定义、边摘要、相关契约及证据目录；支持分页和按需读取。
4. 预览中的 incoming 内容以独立输入视图提供，不将所有未整合图先无条件写入正式图，以免临时重复绑定被当成已接受事实。

Agent 可请求补读，必须说明需要区分哪个含义或检查哪项影响。读邻居不自动继续展开整个邻域。代码记录缺失/截断，Assessment 可要求补读。

### 第二步：Merge Agent 提出修改

Agent 只需回答：哪些是同身份；实质差异如何解释和处理；新的节点与关系如何表达结果。

同身份的描述/实现/口径差异留在该身份内处理。不同身份保留区别，不能为方便重映射强行合并。条件化要有实际可识别且解释行为的条件；不同结果可能都符合请求，不能直接叫冲突。

Agent 输出 identity_groups、edits、changes。关系结构变化由显式 edits 完成，不靠代码从 refs 猜生成。Metric.expression.refs 保留。

### 第三步：代码编译，Assessment 审查

代码依次执行：

1. 解析来源 handle、temporary ID 与现有 canonical；检查模型引用没有越界。
2. 根据已提出的同义组准备节点映射，改写 schema 声明的 ref 槽位；不对描述和 SQL 字面量做字符串替换。
3. 应用 Agent 的节点、边、契约操作到 working copy。
4. 对映射后确实相同的边去重，产生单值 edge alias；范围或 description 语义不同不能仅按 triple 去重。
5. 统一修正 changes 的目标引用、已知分支引用及 relation_metadata 中可安全替换的单值 edge ID。
6. 查找所有删除/拆分/改义对象的外部使用位置；凡不是同义 ID 替换，都要求提案显式处理，不自动选择某个目标。
7. 执行结构、绑定唯一性、分支/关系组和引用校验；无效边返回错误，不静默 drop。

Assessment 只审两件事：

1. **决定是否正确**：identity、差异解释、条件化/竞争/纠错是否有依据，最终定义是否完整原子。
2. **修改是否保义**：对照 changes 的 before/after 和实际图，原受支持含义与消费者是否保留，是否新增无依据约束。

代码验证“引用存在”，Assessment 验证“这些引用确实表达了所声称的含义”。不能把 after 非空当成覆盖通过。必要时修订同一个提案，不引入更多 Agent。

### 第四步：代码原子提交并刷新

节点、边、契约、已处理的消费者和必要关系组一起提交；同时持久化最终映射、变更记录和来源。失败时图及映射都不更新。

更新候选索引；本批 seeds 和改变的 canonical 批次重检索，只有候选/相关内容改变才再调用模型。机械引用替换不触发全图语义再生成；实际定义改变检查直接消费者，若影响继续传播则继续处理，不能提交已知损坏的消费者。

正常结果是整合图及管理记录，不增加 U。工具或预算导致未完成时如实报告运行未完成，不强行分配映射或静默舍弃内容。

## 6. 三个结构对应实例

### 例 A：两个 School 合并

输入 A.school、B.school 经判断为同一实体角色，合并到 G.school。代码重映射它们的关系端点。映射后同义且同范围的重复边归并，产生 edge alias。Agent 不需手写每条受影响关系的映射。

但端点相同并不意味着所有关系相同；如果一条是官网、另一条是招生入口，保留区别。

### 例 B：一条边由两条路径边保留

原始：

```text
A: CharterSchool ─is_a→ School                  (eA)
B: CharterSchool ─is_a→ PublicSchool           (eB1)
   PublicSchool  ─is_a→ School                 (eB2)
```

假设这两项类别包含均被来源支持，处于同一范围，且当前契约允许相应传递。整合后可保留 eB1/eB2，并记录 eA 的含义由该路径表达。

```text
直接 ID 对应：B.eB1 -> G.e1，B.eB2 -> G.e2
结构对应：A.eA -> {G.e1, G.e2} 共同表达
```

不能将 A.eA 自动映射到 G.e1，也不能把 A 的来源自动赋给两条中间断言：A 的原始直接包含本身不证明 CharterSchool 属于 PublicSchool。新中间断言的支持来自 B。结构对应证明旧含义保留，不证明旧来源分别支持新结构的每一项。

如果 relation_metadata 引用了 eA，不能把原 edge ID 直接替换成两个成员：新路径的边未必相邻于原 owner，也未必继续表达该组关系。Agent 必须同步修改该项或保留 eA；代码拒绝悬空/无效组。不能为了简图丢组级知识。

### 例 C：复合 Rule 拆成两个原子 Rule

原 R 同时表达“选择最高聚合分组”和“将选中分组限制应用于详情返回”。来源确实支持两个独立义务时，可由 R1、R2 共同表达。

```text
结构对应：old.R -> {new.R1, new.R2}
```

这是分解，不是两个 identity 同义，不建立 old.R -> R1 的 identity alias。

若消费者引用 old.R，代码列出每个引用位置；Agent 根据角色明确改为 R1、R2 或适当组合。一个单值 ref 不允许机械替换为列表；若对应语义无合法表达，提案不能通过。原来源可以支持多个输出，不需要给它强制分配唯一 canonical node。

## 7. 需要最少改动的现有模块

- `application/merge_graph.py`：保留单值 mappings 用于真正可替换引用的对应；增加仅结构变化需要的 changes/rewrites，不把每个输入都强制映射到唯一节点。
- `operator.py`：将“每个输入节点都有 canonical ID”改成“输入知识都有合法处理记录”：直接保留/同义映射可自动记；结构重写和有据删除需要经审查的说明。不能只检查有一条记录就认为语义保留。
- `transactions.py`：从单 group preview 拓展为标准局部操作 batch，复用 GraphManager 原子验证及 revision。
- `edges.py`：机械端点替换与相同事实归并保留；一对多路径或结构替换由显式提案负责；无效边不应静默丢失。
- `references.py` / `relation_metadata.py`：继续只做已声明槽位的安全替换；一个旧引用对应多项时要求明确改写。
- prompts / Assessment：精简为上述三块提案与两项语义审查，按需读取类型规则，不重复注入大清单。

结构重写记录不是额外业务 ontology，也不参与在线 SQL 的隐式推理。在线消费者应使用整合后真实图；原来源到新结构的记录用于审计、评估和明确迁移。保留前后 revision 可追溯历史，不需要对每次提交重新生成全历史多对多映射矩阵。

## 8. 能力边界

语义保持一般不是可由代码完备判定的图同构；节点/关系重写也不一定两边完全等价，新图可以整合更多有据知识。Assessment 针对原来受支持的含义、条件和角色检查保留，而非“看起来都连上了”。

本方案精简了模型任务和映射机制，但没有解决 v62 中任意多对象关联冲突的通用表示问题。changes 不能代替 alternatives，来源记录也不能让互相矛盾的普通边合法共存。纯关系竞争仍需单独确定最小图内表示，不借本轮简化暗中新增通用分支系统。
