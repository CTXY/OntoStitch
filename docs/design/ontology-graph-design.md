目标是组织可复用的 NL2SQL 业务知识，允许多种正确的层级组织，不追求唯一标准图或全局最少节点。本文只形式化可明确解释、检查或推导的条件；不以未定义的 Valid、Supported 等函数代替业务判断，不新增通用逻辑语言。

## 1 范围与基本解释

### 1.1 节点与关系

- 物理节点：Table、Column、DimensionValue，来自真实 catalog 或已核实的数据值。
- 语义节点：Concept、Metric、GenerationRule、Event。
- 不新增 Entity、BusinessObject、Process、Constraint 基类，不强制状态/属性/类别角色枚举。
- 关系显式保存于图的 edges 中。Agent 直接生成业务边，不在读取、展示或检索阶段通过通用 refs 重建业务边。
- Metric.expression.refs 保留，用于公式占位符和输入校验；不是通用业务边推断机制。
- 每条边有唯一 ID、谓词、两个端点、非空 description 和可追溯来源。不增加 qualifier 或统一 participant-role 字段。
- 新业务谓词允许扩展，但必须同时保存明确的类型契约，不只增加一个名称。

### 1.2 业务指代与断言含义

Ontology graph 可以包含业务类别、任务相关的具体业务对象，以及它们的数据库表示、计算和生成知识。它不要求枚举全部数据实例。每个节点的指代层次和每种关系的断言含义必须明确。

Concept 的定义说明其实际指代，不增加类别/实例等角色字段。由 Question、SQL、字段含义及记录粒度共同判断，不因名称、一个数据库取值或一行记录就认定它是类别或具体对象。任务相关的具体对象仍须满足 Concept 的有效绑定和语义最小化要求。

业务边按两端的实际指代和谓词契约解释。两个类别间的联系不自动表示具体对象配对、每个成员必有该关系、唯一值、完整记录或可执行 JOIN；涉及具体对象时也不能扩大为全部同类对象的普遍事实。is_a 仍只表达可比较类别之间的包含，不因容许具体对象而放宽它的含义。

更强的存在性、基数、互斥或覆盖声明必须明确表达其范围。图中缺少一条边，不表示业务关系为假；数据库缺值，也不等于业务对象或事件不存在。

同一谓词可以允许多个业务来源类别；不能把每条类型关联分别翻译成同时成立的全局 domain 要求，从而错误要求所有来源同时属于全部类别。

### 1.3 当前不需要的复杂度

不要求完整 OWL 转换、通用定理证明器、所有实例入图、所有 description 形式化、所有分类两两连边或所有重复模式建立抽象节点。本文只规定少量确定的推导；其他业务组织由 Agent 结合定义与证据判断。

不单列“推理/归纳/约束检查”符号体系。只保留一个操作区别：按已有规则推出结论时给出规则和前提；提出新的概念或一般化结构时说明共同含义及保存的差异，不能称为逻辑必然。

## 2 核心要求

### 2.1 证据与声明一致

综合 Question、SQL、evidence、已提供字段说明及必要的只读数据库探索判断业务含义。SQL 是 case 实现依据，不是任意业务规律的证明。不同来源有真实竞争时保留冲突，不能按来源顺序静默选一个。

语义拒绝必须指出具体契约违反，或同范围内与给定证据相矛盾的断言。SQL 未投影某字段、没有逐字描述某联系、未观察到某事实，本身都不是反例。合理业务解释和一般化不因缺少显式证明被拒绝，也不等于已证明普遍真理。

不因缺少可选节点、可选层级或某种偏好的组织方式判错。不使用节点数、类型覆盖率或必要知识遗漏清单作为独立质量指标；知识缺陷通过具体错误、矛盾或信息丢失定位。

### 2.2 业务指代与物理表示分开

名称、定义、绑定和关联角色必须一致。名称/编码可指代业务对象；图节点 ID、记录 identifier、业务名称不是同一层含义。姓名不证明唯一人物身份，主键不自动证明跨表/跨时间业务身份或每行均为同种业务对象。

规范名称选择能代表整合含义且符合 Question 用语的表达，不按最短、频次、输入顺序或 SELECT 列名机械决定。同名不证明同 identity，不同名也不证明不同 identity；不要求全图名称唯一。

### 2.3 最小化只约束节点内容

Concept / Metric：不能将可独立匹配的 NL 含义捆绑成一个节点。判为不最小化时，必须给出具体拆分：各部分表示什么、分别匹配什么字段/值/操作，以及如何组合保留原义。不能只凭词数、targets 数量、公式复杂度判断。

若当前证据与 NL 场景下存在如下分解：

\[
n\equiv u_1\oplus\cdots\oplus u_k,\quad k\geq2,
\]

其中每个 u_i 都是完整、可独立匹配的语义单元，\(\oplus\) 表示保留原义及必要限制的 NL 组合，则原节点不满足最小化。“独立”指当前 NL 组合中的不同语义与匹配职责，不要求物理输入互斥；展开业务定义或公式，不自动构成 NL 分解。同一对象由名称、identifier 分别表示，或一个全名由 first/last name 联合表示，都不是仅凭多字段即可拆分的理由。

GenerationRule：一个最小、完整、可复用的行为选择。若改变其中一个选择而另一行为仍完整、可独立适用与评估，应分开；同一行为的必要实现步骤可以共同存在。SQL 子句数、intent 标签数、解释条目数不是动作数。

这些条件由语义评估判断，不要求唯一 NL 原子词典、确定性分词器或“未证明最小化即失败”。不另设 uncertain/U 节点状态。

### 2.4 保存含义、冲突与来源

合并或重构必须保留有意义的区别、匹配条件、公式口径、生成选择及真实冲突。不同 case 的偶然地点、日期、记录集合和字段后缀不能自行消除竞争，也不能人为制造竞争。

真正冲突保存为同一决策/身份的完整 alternatives，保留各自内容、适用条件、来源及分支关系；不能只保留几句冲突说明，也不能保留普通副本绕过已保存冲突。

已明确定位的抽取/表达错误可纠正或弃用，并记录具体契约违反或源证据矛盾及来源去向；保存来源不等于保留错误断言。仅因跨 case 表达不同不能判为错误，可同时成立的互补说明或等价 SQL 写法也不是冲突。不为保全文字而强造 alternatives。

来源映射允许多对多；它不表示每个原始来源都支持每条结果边。删除、合并、拆分的断言必须说明去向或有依据的丢弃，不能把所有来源广播到所有结果。

### 2.5 不把结构信号当判定规则

三角形、环、同谓词多端点、相同物理端点、同字段多值 Concept，均用于定位待检查区域，不自动决定删除、合并或新增节点。

一般业务图不强制为树或 DAG。只有当前非递归计算的 Metric 依赖必须无环。相互 is_a 表示集合相等，应检查等价组织，但不自动证明业务 identity 相同。

## 3 节点及其要求

### 3.1 物理节点

| 类型 | 含义 | 要求 |
| --- | --- | --- |
| Table | 物理表 | 真实名称、结构和来源明确；行粒度/覆盖范围由初始 metadata 说明 |
| Column | 表内字段 | 有唯一物理 Table owner；ID 与真实字段名区分 |
| DimensionValue | 指定字段下的真实类型和值 | 有唯一 Column owner；值已核实，不能只保存裸字符串 |

DimensionValue 默认使用可读、可逆编码，不新增 SHA-256 值身份。具体转义及旧 ID 兼容沿用实现约定；实际值从 value 字段读取，不通过拼接节点 ID 生成 SQL。同字面值跨字段、不同数据类型或不同编码版本不自动视为同一个值。

### 3.2 Concept

Concept 表达一个最小完整、可复用的业务含义，可涉及对象、角色、属性、类别或存储量。由语义、场景和数据决定表示方式，不设置学校领域或状态/类别的确定性决策树。

要求：稳定 ID、可读名称、明确含义、真实来源和非空有效 targets。不是每个词、字段和值都应建立 Concept；其独立匹配或业务组织作用必须清楚。

新的 case-level Concept 仅绑定 Column / DimensionValue，不直接以 Table 为 target。历史 Table target 的可读兼容，不代表新抽取许可。高层 Concept 也需有实际业务含义和有效绑定，不能是无锚点标题。

targets 外层的每个 item 是一种完整匹配；内层多个端点联合完成该匹配。不同表示应分组：

    School
      targets = [[schools.CDSCode], [schools.School]]

    Administrator
      targets = [[AdmFName1, AdmLName1],
                 [AdmFName2, AdmLName2],
                 [AdmFName3, AdmLName3]]

这些例子不证明匹配组可互换、全部返回、合并补空、列顺序、跨槽位同一身份或相同覆盖范围。联合条件与复杂匹配保留完整表达式，不能从端点集合恢复逻辑。

类别等值匹配连接具体 DimensionValue；value_of 表明其字段归属，不用该 Concept 的额外 Column 绑定重复表达同一等值条件。

不同 Concept 的 targets 可以重合；直接 grounded_on 边满足唯一 owner 要求。一个 Concept 可以连接多个正确物理端点，不要求每个 target 引用都产生直接边。未直接连接的表示仍在 targets 中完整保存。

### 3.3 Metric

Metric 必须有定义业务量的真实计算，保留 expression 和 expression.refs。仅映射存储数量的是 Concept；field×1、field+0 或单纯类型适配不构成业务计算。

真实计算仍须通过 NL 最小化。School + count + monthly average 之类独立匹配职责不应包装成整句 Metric。FRPM eligible count、Enrollment 等存储量为 Concept；具有明确总体、粒度和定义公式的 eligibility rate 可以是 Metric。例子只说明语义边界，不构成关键词规则。

expression 的占位符与 refs 一致；操作数、单位、粒度、总体及必要常量明确。保留实际 COUNT 操作数、DISTINCT、NULL、连接粒度、分母处理与运算顺序，不因发现 identifier 就替换 name 计数。复杂定义可以包含聚合，不能按函数或运算符数量机械拆解。

### 3.4 GenerationRule

GenerationRule 服务于 NL2SQL 的有意义实现选择。condition 说明适用前提，action 说明最小完整行为，reason 解释依据和必要结果；检索 triggers 不代替 condition。

静态术语到字段/值的匹配由 Concept 表达，定义公式由 Metric 表达。选择使用哪些表示可成为字段选择 Rule；已选内容的列顺序/行列形状是另一种决策。普通操作出现、多种等价 SQL 或假想错误不足以创建 Rule。

Direct 和 error-driven 使用同一 registry 语义，不设 direct/repeat-only intent 分区。已有 intent 不能被强行扩义；允许多个标签，也允许提出新 label 并说明含义、缺口和有依据的实现差异。新 label 的全局发布生命周期不在本文中强制新增。

参数化偶然年份、地点、阈值或 K，保留定义固有常量和必要业务操作数。可引用相连 Concept/Metric，附局部 SQL pattern 帮助理解，不复制整条 Gold SQL 或要求唯一 SQL 写法。泛化后不能改变已给案例要求的行为。

top-K 可包含选中实体及透传其被请求属性；“固定选择第一邮箱还是全部邮箱”是另一个可变选择。不能因 Assessment 将前者写成两条说明，就机械判为复合动作。

声称实际错误、执行结果、profiling 分布时必须有对应记录；未发生的尝试不能编为 reason。没有额外选择的日期/缺值限制应写在关系或定义中，不强造 Rule。

### 3.5 Event

Event 表示有证据的事件类型/模式，不默认表示一行一个事件或某个已枚举实例。创建时需识别发生行为、参与对象及其角色、至少时间或地点之一，并有这些信息关联到同一发生的依据。

参与者可以是学校等业务对象，不要求人物。日期列、动词、状态值、事件名称或一次 JOIN 单独均不充分。同表多角色不授权笛卡尔积配对。

如声明 targets，其直接 grounded_on 必须与 targets 一致；否则也必须通过明确的关联结构和数据库依据解释事件。具体锚点接口沿用实际 schema，不新增未实现的必填字段或凭空放宽结构证据要求。不能由非空日期反推事件定义、完整历史、可计数性或重复发生。

## 4 每类关系的契约

### 4.1 统一约定与符号

每个关系类型说明合法端点配对、方向、业务角色/含义、必要校验及允许的推导。谓词注册定义不被单条边的 description 覆盖。新谓词可以扩展，不要求扩成更多核心类型。

以下公式均针对同一数据库、相容条件和有效冲突分支中的完整图。V 为有效节点，P 为物理节点，C 为 Concept；T(c) 是 targets 的分组列表。边记为 r(a,b)。不为这些符号增加存储字段。

所有边均要求：

\[
src(e),dst(e)\in V,\qquad
(type(src(e)),type(dst(e)))\in Sig(r).
\]

Sig 是合法配对，不是源类型与目标类型的任意笛卡尔积。例如 is_a 仅允许 Concept→Concept 或 Event→Event。

### 4.2 belongs_to：字段的物理表归属

端点：Column→Table。完整 catalog 中每个 Column 恰有一个所属表，与 column.table_ref 一致：

\[
belongs\_to(c,t)\ \Longleftrightarrow\ table\_ref(c)=t.
\]

它不是业务组成或属性归属关系；与 value_of 相连时可用于定位物理来源，但不生成业务边或同 identity 判断。

### 4.3 value_of：物理值的字段归属

端点：DimensionValue→Column。完整 catalog 中每个维值恰有一个所属字段，与 value.column_ref 一致：

\[
value\_of(v,c)\ \Longleftrightarrow\ column\_ref(v)=c.
\]

值及类型须由该字段核实。相同字面值不授权跨列合并。单字段单值记录也不自动证明业务对象跨时间只能有一个类别。

### 4.4 joins_with：物理连接条件

端点：两个不同 Table。column_pairs 是经过确认的完整等值连接条件：

\[
J(t_1,t_2)=\bigwedge_i t_1[c_i]=t_2[d_i].
\]

每个 c_i、d_i 属于正确一侧；复合键不能少列。cardinality 等额外声明须与其方向和依据相符。反向使用须交换列对及方向性说明；不必另存反向边。

连接条件不决定 INNER/LEFT 等查询策略，不证明业务身份、唯一覆盖或结果粒度。连接路径可以逐步执行，但不推出首尾表间一条新的直接连接。

### 4.5 grounded_on：直接物理表示或输入

端点：schema 允许的语义节点→物理节点。它记录表示/实现依据，不是业务包含或普通相关性。

Concept 的直接绑定端点必须属于其有效 targets：

\[
grounded\_on(c,p)\Rightarrow p\in\bigcup T(c).
\]

同一有效图中的一个物理端点最多有一个直接规范 Concept owner：

\[
\forall p\in P,\quad
|\{c\in C:grounded\_on(c,p)\}|\leq1.
\]

该式统计不同 Concept，不统计 targets 中出现次数。description 不能自行创建豁免范围。共同绑定是身份检索信号，不是节点相同的证明。

Metric 按 4.6 的直接物理 refs 校验。Event 如有 targets，边必须属于这些 targets。schema 对 GenerationRule 的端点许可不自动使 trigger 列成为绑定；若保存 Rule 的直接物理边，必须明确其实际操作数/实现依据，不能代替 applies_to 或重复静态匹配。

grounded_on 不传递、不沿 is_a 复制、不授权 JOIN。联合匹配中的某一条物理边不表示它单独充分实现 Concept。

### 4.6 depends_on：公式直接语义输入

端点：Metric→Concept/Metric。令 S(m) 为 expression.refs 中的直接语义输入，P(m) 为其中的直接物理输入，分别满足：

\[
\{n:depends\_on(m,n)\}=S(m),
\qquad
\{p:grounded\_on(m,p)\}=P(m).
\]

\[
placeholders(expr_m)=keys(refs_m).
\]

重复使用一个输入不必重复边。当前非递归 Metric 计算的 Metric→Metric 直接依赖必须为 DAG。依赖可达性用于分析间接输入和排序，不将间接输入补成同谓词的直接边。

### 4.7 applies_to：生成决策的作用对象

端点：GenerationRule→Concept/Metric/Event。它明确规则涉及的业务操作对象，必须与实际 action 和 condition 一致；不是一般“相关”关系。

适用某次请求必须同时满足 condition 和当前分支要求。applies_to 本身不是触发条件，不声明作用对象都必须执行规则；多个 Rule 指向同一节点不证明同一决策或相容。Rule 作用于父类时，不自动复制成对所有子类的无条件规则，必须按实际条件判断请求适用性。

### 4.8 is_a：业务类别包含

端点：可比较的 Concept 类别之间或 Event 类别之间。令 Ext(A) 表示同范围内类别 A 的对象集合：

\[
is\_a(A,B)\Rightarrow Ext(A)\subseteq Ext(B).
\]

不声明真子集、立即父类或一定有实例。物理对象群体、属性维度和具体值不能仅因名称相近互换为父子类。

同范围、相容前提下允许传递：

\[
is\_a(A,B)\land is\_a(B,C)\Rightarrow is\_a(A,C).
\]

双向包含给出集合相等，但不自动决定节点身份合并。兄弟类别不默认互斥、相交或覆盖父类。子类可以由属性条件定义；不要求额外文档、专属属性、动作或 Rule，也不因类别可重叠或可变化就强制改为属性。

is_a 不复制 targets、不补非空条件、不执行 JOIN、不搬移属性直接归属。

### 4.9 has_attribute 与具体业务关系

has_attribute 是抽象契约家族，禁止直接生成该谓词的边。允许具体谓词可选 extends=has_attribute；此处是契约字段/端点的继承，不自动等于 OWL subPropertyOf 或新的业务推理规则。

具体业务谓词说明两端实际角色、方向和必要范围。例如：

    School ── has_administrator ──→ Administrator
    Administrator ── has_contact_email ──→ Email address

属性应连接它直接描述的业务对象/角色或适用子类。上述路径不推出 School 自身 has_contact_email；存储在同一表更不是其依据。具体谓词可以独立扩展，不要求全部纳入属性关系家族。

令 D_r、R_r 分别为该谓词允许的来源、目标业务角色所对应的对象/值集合，则其实例角色约束为：

\[
r(x,y)\Rightarrow x\in D_r\land y\in R_r.
\]

本式解释该谓词的角色；涉及具体对象的联系与类别间的联系按各自指代解释，不将类别连线冒充实例事实或全称存在断言。确需唯一、必有等限制时，必须明确它作用于业务实例、来源记录还是时间切片；自然语言限制由 Agent 评估，不自动交给代码执行。

category_of 可作为已登记的业务谓词，说明类别/取值含义属于哪个业务分类维度，不替代 is_a。若节点表示对象类别，须明确其分类条件，不能把对象集合直接当作值集合。它不是新增核心关系，也不默认传递。

事件参与关系采用具体业务角色谓词；不以统一 has_participant 加 qualifier 压缩不同角色。一般业务谓词不默认启用对称、传递、逆关系或路径组合推导；这不等于声明关系非对称、非传递或不存在逆关系。推导性质不能由名字猜测。

### 4.10 description 与 relation_metadata

description 简洁说明两端的实际业务联系、角色及必要限制。可以说明“某记录编码在此来源识别学校”“缺少开学日期不表示未开学”，不堆积 profiling 数字、字段百科、完整 SQL 或审查过程。只说明 stored on record 不足以代替业务联系。

Concept 可选 relation_metadata，每项沿用 id、edges、description：引用至少两条相邻、同谓词、同相对方向且分支相容的边，用于单边无法表达的组级含义。

不为每对兄弟节点补边；也不要求每组都有说明。若声明互斥或穷尽，其含义分别是：

\[
\forall i\ne j,\ Ext(C_i)\cap Ext(C_j)=\varnothing;
\qquad
Ext(B)=\bigcup_i Ext(C_i).
\]

二者独立，不由同层、同字段或当前无交集推出。允许类别重叠不等于已观察到共同实例；没有声明互斥，也不是一项“已证明重叠”的事实。

relation_metadata 和 description 的自然语言不自动变为机器推理公理。若未来某项限制需要自动推导/验证，应另行明确其可执行表达，不要求现在设计通用 constraint registry。

## 5 允许的推导与去冗余

### 5.1 当前采用的最小能力

1. 业务类别推导采用 4.8 的 is_a 传递。
2. 计算输入采用 depends_on 的路径可达性分析，但区分直接/间接依赖。
3. catalog 归属与已确认 JOIN 用于定位来源及合法查询路径。
4. 具体业务路径可检索、解释或用于有据的查询规划；可达不等于首尾存在相同谓词。

不默认启用一般业务传递、逆关系或属性链。不因新谓词已注册就自动获得这些语义。若确需新增规则，须先明确前提、结论、方向、有效范围，再核对其与实例/类型层次是否一致。当前不要求通用推理器。

### 5.2 有效范围、冲突与推导记录

所有推导只使用在同一判断范围同时有效、相容的前提；不能将互斥 alternatives 并成一组无条件事实。只有各相关分支共同成立的结论才能无条件复用。

派生结论保留所用规则、前提边和适用条件/分支，优先作为可查询派生视图，不全部写为作者边。否则会人为增加冗余边与重复评估。

推导不生成新 Concept 或事件实例，也不选择冲突分支。description 中“未必记录日期”不产生“已观察到缺失日期”的数据事实。

### 5.3 重复与可推导冗余

重复断言指相同规范含义、端点、角色与适用范围。字符串相同只是特例；不同描述可能同义，不同范围也不能仅按端点合并。

在每个相关有效范围/分支内，G 表示该有效图，D 仅包含其中本次拟删除的断言，R 为明确允许的规则：

\[
\forall a\in D,\quad (G-D)\vdash_R a.
\]

这是可推导冗余的判据。检查的是最终保留图，不得使用被删断言自证或让多个删除互相循环支持。

删除还必须保留材料性限制、独立来源和实际消费者能力。公式所需直接输入边、catalog 归属或仍需显式读取的事实，不能只因存在路径就删除。尚不支持派生读取的消费者不能被假定会恢复已删内容。

不追求全图最简表示，不强制 Event 压缩、节点数最少或唯一正确层级。不能证明重复/推导时，不因“看起来绕”删除。

## 6 抽取、整合与结构调整共同遵守的规则

### 6.1 抽取与错误驱动

读取任务、已有知识和相关指引；必要时只读探索；原子提交节点、绑定及显式边；对最终保存的同一图做格式、语义与 SQL replay 检查。replay 正确不能证明 ontology 语义正确。

不通过确定性领域关键词生成、拆分或修复业务含义。通用代码可管理 ID、catalog、精确字段校验和来源，不决定业务 identity 或层级。

可选漏边兜底仅根据已保留且含义明确的引用补全并保存，不猜业务边。读取/展示阶段不补。Repair 可修改所有四类语义节点及关系，错误定位到最小知识单元，不追加完整查询作万能修复。

### 6.2 从具体知识组织出更通用的结构

允许 Agent 新增必要高层 Concept、规范指代、合并/拆分/删除不合理节点并重组关系。默认保留已接受的知识，不常规重新编写所有节点。

多个 Concept 连接同字段不同值时，检查是否有共同业务维度，以及该维度是否值得独立表达。若存在则复用；确有用途且满足绑定/最小化要求时可新增。共享字段只是线索，不机械决定共同父类、互斥、穷尽或必须新增节点。

同样可以从重复角色、局部限制或规则找到共享组织：单边限制放 description，多边共同含义放 relation_metadata，有独立意义的生成选择才属于 GenerationRule。不增 Constraint 节点。

每项一般化简述共同含义、所组织的具体知识、保留的条件及竞争差异。合理一般化无需预见未知案例，但不能删除必要前提、掩盖冲突或改变已给案例要求的行为。新增抽象不存在本身不是错误，也不设抽象数量或信息价值分数门槛。

### 6.3 命名或节点重构后的关系检查

姓名/identifier 可指代业务对象；若只是同一指代的规范化，允许协调 name、aliases、definition、description，不改变 identity、绑定或行为。

实际新增、合并、拆分、删除节点则必须明确保存知识去向，并检查受影响入边/出边的角色、方向、条件和消费者。不能仅重映射 ID 后沿用所有旧边，也不因局部重构重新评估无关节点。

## 7 检查与 Agent 分工

| 检查 | 主要责任 |
| --- | --- |
| 字段、ID、引用、合法端点配对、物理 owner、匹配组形状 | 代码 |
| 公式 refs 与直接边一致、非递归计算无环、分支引用合法 | 代码 |
| 业务指代、最小化、直接属性归属、声明强度、条件与相容性 | 相应语义 Agent |
| 已明确规则的推导、证明前提和受影响结果重算 | 代码；不发明新业务规则 |
| 新抽象、层级组织、关系意义、真实 identity 或冲突 | Agent，结合证据 |
| 来源去向和序列化完整性 | 代码；来源对某事实的实际支持由 Agent 判断 |

节点阶段评估实际节点内容和匹配组。Reconciliation Writer 负责检查本次选定区域的关系、层级、分组和必要重构。代码确认没有实际图变更时，直接结束该任务，不调用关系 Assessment，也不另设第二次区域检查。

有实际变更时，关系 Assessment 只评估变更及其必要的关联影响，不重复扫描整片区域。未改边仅作为判断变更所需的比较背景；节点内容仅复核新改部分及变更直接影响的含义。若未改 Rule 的 action/condition 直接决定该变更的相容性，可定向核对该部分，不逐批重新枚举所有未变 Rule 的 decisions/reasons。此处不取消节点整合阶段已有的 Node Assessment。

关系首屏提供节点类型/名称/aliases/含义、边及 description、相关证据、必要契约和归纳线索。只按明确缺口读取额外字段，不为“完整看一遍”获取全部节点、物理 metadata 或重复 evidence。原始记录及来源账本由代码完整保存；轻量模型输入不等于删除它们。

必要的节点内容变化只评估实际受影响内容及消费者。动作原子性按可独立改变的选择判断，不按 independent_decisions 列表长度机械裁决。

评估反馈给出具体对象及契约违反、证据矛盾或材料性知识丢失；普通表达偏好不阻断接受。格式通过、SQL 通过、来源审计通过、单次模型 accept 均不能独立证明全部语义正确。

## 8 不变的项目边界与实施说明

metadata 仅由初始 database profiling / file extraction 构建供 offline 读取；训练不进行 NLQ–SQL metadata 抽取、error-driven metadata 更新或优化。只读数据库探索仍可帮助理解 ontology。该模块不属于论文使用与评估范围。

本文不改变原始数据库，不引入领域专用 deterministic rules，不强制全量图重新运行，不因文档更新声称新 prompt、轻量工具或恢复调度已上线。

实际实现仍须逐项核对 root schema、资产模型、共享指引、各 Agent 输入/工具、校验和图消费者。旧快照可读取不等于新写入许可。既有值 ID 转义、生命周期、撤销、版本、ID 重映射和局部事务细节保留在实施文档中，不重复成为 ontology 语义公理。

## 9 OWL / SHACL 的参考边界

OWL 提供类、属性、限制与推理的明确语义，不规定本项目 NL 最小化、数据库绑定唯一性或生成决策准入。[OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

OWL 的 domain/range 通常用于推出实例类型，并非“端点未标类型就拒绝输入”的数据库校验。[Domain and range](https://www.w3.org/TR/owl2-primer/#Domain_and_Range_Restrictions)

自然语言 annotation 不自动改变逻辑结论；本文也不把 description 当成可执行公理。[OWL annotations](https://www.w3.org/TR/owl2-syntax/#Annotations)

图满足指定条件的检查可借鉴 SHACL，不必为此迁移为 RDF 或采用完整 SHACL 执行器。[SHACL Recommendation](https://www.w3.org/TR/2017/REC-shacl-20170720/)

本文是自定义的 NL2SQL ontology 规范，不宣称实现完整 OWL、OWL RL 或完备的自然语言推理。


### 业务属性归属与层级替换的边界（实现澄清）

不能仅凭字段存储位置、非空值范围，或某类之外也有该属性，推翻一个原本成立的类别业务联系。只允许 is_a 传递时，

\[ C \subseteq B,\ R(B,p)\not\Rightarrow R(C,p),\qquad R(C,p)\not\Rightarrow R(B,p). \]

这里 R 是普通类别业务联系，不是已另行声明继承契约的实例级全称属性。因此父类/子类上的业务边不自动互相替换。迁移或删除须有原归属错误的业务/同范围证据，或明确允许的保义推导；仅仅“概括得更广”不足以删除原事实。
