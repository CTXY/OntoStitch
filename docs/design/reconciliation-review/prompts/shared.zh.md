# 图关系与节点要求

## 基线与指代

- 已接受节点和分支是关系判断的前提，不重新审计其事实、公式、理由或原子性。
- 以下节点准入要求仅用于新建节点或实质重构新引入的内容。
- 图可表达业务类别、任务相关具体对象及数据库表示、计算和生成知识，不要求枚举全部实例。
- 明确节点实际指代层次和关系断言含义；不因名称、字段值或单行记录判断类别、具体对象或身份。
- 无需增加角色字段或新的节点基类；多字段、长名称或展开公式本身不证明应拆分节点。

## 按节点类型检查新建或重构内容

### Concept

- 表达最小完整业务含义；名称或 identifier 可以表示业务对象，不必另建名称或代码 Concept。
- 有非空有效 `targets`；新建 Concept 使用 Column / DimensionValue。
- 外层 targets 是不同完整匹配，内层是联合匹配，不规定 SELECT 哪些字段或如何呈现。
- 仅在可拆成独立、完整可匹配的含义，并能说明保义组合时，才主张拆分。

### Metric

- 定义真实业务计算，保留完整 `expression` / `refs`、单位、粒度与适用条件。
- 存储量、恒等计算或包装整句请求的聚合组合，不因此自动成为 Metric。
- 最小化按自然语言业务含义判断；不能仅因公式较长而拆分。

### GenerationRule

- 定义一个最小完整、可复用的生成选择，保留其 condition / action 和理由。
- 一个必要实现可含多个步骤；按可独立改变的行为判断，不能按 SQL 子句、intent 标签或解释条数拆分。

### Event

- 有行为、参与对象、至少时间或地点之一，并有这些角色关联到同一事件的证据。
- 日期列、动词或 JOIN 单独不足以创建事件。

# 关系契约

## 共同要求

- 所有边显式保存，端点类型正确，`description` 非空并有可追溯依据。
- description 解释业务联系及必要限制，不堆积存储 metadata。
- 按两端实际指代解释普通业务边；类别联系不自动声明实例配对、必有、唯一或完整记录。
- 具体对象联系不能扩大为所有同类对象的普遍事实。
- 属性连接其直接描述的业务对象，不能沿普通业务路径转移归属。
- 存储位置、非空覆盖率或“该类之外也有此属性”，均不能单独决定业务归属或证明该联系错误。

## 各谓词的含义与限制

- `is_a`：同范围、可比较类别的集合包含；不是具体对象归属、属性联系或物理映射。同范围且分支相容时可传递，不复制 targets 或 Rule，不假定兄弟互斥或穷尽。
- `grounded_on`：直接物理表示或输入，与 targets 或公式一致；Concept 规范 owner 约束见下一节。
- `depends_on`：Metric 公式的直接语义输入，与 `expression.refs` 一致。不能将间接依赖补成直接边；非递归计算依赖必须无环。
- Metric refs 指向 Column / DimensionValue：用 `grounded_on` 表达直接物理输入；指向 Concept / Metric：用 `depends_on`。不把合法物理输入改成语义输入，不仅因没有 depends_on 就判断缺边。
- `applies_to`：Rule 实际作用对象，结合 condition 和所选分支判断；不自动触发，也不沿层级无条件继承。
- `belongs_to` / `value_of`：Column→Table、DimensionValue→Column 的物理归属，与 catalog 一致，不表示业务归属。
- `joins_with`：经过确认的完整连接列对；不证明业务 identity，不决定查询 JOIN 类型，也不允许直接连接首尾表。
- `has_attribute`：抽象家族，不直接生成边。使用或登记具体业务谓词，写明直接主体、方向及范围；不得用存储关系替代业务关系。

## Concept 直接 owner

- 在同一数据库、适用范围及相容分支组成的有效图中，每个物理端点最多有一个 Concept 直接 `grounded_on` owner。
- 发现竞争时，判断是身份应合并，还是应调整直接绑定及业务关系；不能直接认定两个 Concept 相同。
- 不同 Concept 可以保留重合 targets；targets 不是必须逐项生成的出边清单。
- 不要求每个 Concept 或每个 target 都有直接 grounded_on。
- 移除竞争绑定时，核对保留规范 owner、targets 和业务关系是否保义；不能仅因少一条直接绑定而拒绝，也不能要求恢复冲突边。

## Concept 关系组

- `relation_metadata` 仅用于 Concept，不用于 Rule、Metric、Event 或边。
- 形状为 `[{id, edges, description}, ...]`，描述同谓词、同相对方向、分支相容的多条相邻边的组级含义。
- 保留材料性顺序、重叠、互斥或覆盖说明；不是重复单边说明，也不强求每组都生成 metadata。
- 描述文字不会自动成为可执行公理。

# 图组织与保义修改

## 层级与抽象

- `is_a(A,B)` 要求同范围内 `Ext(A) ⊆ Ext(B)`。
- 共同父类、共同字段、三角形、环或平行边只是线索，不证明互斥、覆盖、身份相同或错误。
- 一般业务图不要求无环；计算依赖遵守非递归 DAG 约束。
- 可以组织共同业务维度或更通用表述，但须说明共同含义、具体知识及仍需区分的条件和实现。
- 新增 Concept 仍满足绑定与最小化要求；不为每个重复模式强建抽象。
- 不凭结构相似增加唯一、必有、互斥或穷尽声明，不省略条件扩大行为要求。

## 重复与冗余

- 同一规范端点、相同谓词含义及适用范围下的同一事实可以合并，保留兼容说明与来源。
- 相同端点角色不足以合并；描述文字不同也不必然表示不同事实。
- 删除集合 D 中每条断言 a，须能由最终保留图 `(G-D)` 按已允许规则 R 推出，即 `(G-D) ⊢_R a`。
- 除同范围 is_a 传递外，其他推导规则必须由输入明确提供，不能根据谓词名或路径自创。
- 不用已删除断言自证，不循环互证；间接路径不能自行替代公式直接输入或物理归属。
- `C is_a B` 不自动允许在 `R(B,p)` 与 `R(C,p)` 之间转移断言；须证明旧关系错误或按允许规则保义。
- 所有相关分支分别检查，不能混用互斥分支前提；不丢失材料性限制、来源及消费者能力。

## 允许纠正与拒绝标准

- 明确违反契约、与源证据矛盾的关系断言，以及本次整合新引入的错误，可以有依据地纠正或弃用，并记录理由与来源去向。
- 不能借此重新否定已接受输入节点知识，也不能因跨 case 差异任意判某来源错误。
- 拒绝必须指出具体契约违反、同范围证据矛盾或材料性知识丢失。
- 未投影、未逐字描述、未观察到，不单独构成矛盾；合理泛化无反例不等于证明普遍真理。
- 风格偏好、可选抽象缺失或其他有效组织，不是拒绝理由；来源覆盖也不证明语义正确。

# 当前记录与读取范围

- `source_presence` 区分归档退役记录与存活 candidate；不要把归档对象算成当前普通副本。
- 同 ID 已改变时判断 candidate 版本；报告缺失时指出当前缺少的含义。
- 节点字段：`node_type`、`name`、`description`、`properties.definition/action/condition`；边字段：`edge_type`、端点和 `properties.description/alternative_ids`。
- focus 结构字段完整；邻居摘要不更名，未展示字段可读，不证明缺失。
- 只为具体关系判断或必要节点重构读取缺失内容；不因存在 alternatives 就重新审计每个完整分支的 reason 或必填字段。

## 节点阶段的关系义务

`node_relation_followup`、`node_relation_obligations` 输入封装（包括其中的 diagnostics/relation_followups），或 `structural_diagnostics` 条目，都是必须完成的保义结果要求，不是可选的检查信号。读取其原始关系记录及原始 ID 到当前 ID 的映射；仅凭某个 ID 已退役，不能证明其知识已经被移除，也不能证明可以丢弃该知识。以已接受的节点内容为基线，完成每一项给定义务，保留有效角色、配对含义、来源与分支作用域。不得仅为避免表达节点关系而重新审议节点定义。如果节点内容本身有缺陷，应指出具体反例。

ID 重定向与完全重复项的删除属于机械处理。尚未确认同一身份的不同端点仍保持不同。`properties.alternative_ids` 限定起点 owner 的分支，不能选择终点节点的某个 alternative。新增 alternatives 不会自动继承仅属于旧版本的断言。即使 Writer 没有提出修改，独立 Graph Assessment 也必须核查每一项要求的结果；无操作不证明某项义务已经解决。
