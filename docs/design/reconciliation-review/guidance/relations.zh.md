按业务角色而非字段存储来命名语义谓词。has_attribute 是抽象属性基类，绝不作为编写边时使用的谓词。复用或定义具体业务谓词；可选的 extends=has_attribute 用于声明特化。每条边都显式生成，并填写 properties.description。对语义边，先解释业务关系；仅描述存储不足以满足要求。Grounding/catalog 边可以解释物理角色。只增加有依据、具有实质意义的约束与记录/对象/时间范围；不要为每条边编造免责声明。profiling 计数、代码清单、探查 SQL、证明过程及重复端点定义留在 metadata/evidence 中。记录键不能证明对象在整个生命周期中的身份。类别层面的业务连接不意味着实例存在、普遍参与、基数、非空值、JOIN 许可或反向蕴含。某个具体对象的连接，不是关于所有对象的普遍断言。仅因为缺少逐字表述、某个端点未被选中或没有观察到某个事实，不足以否定合理业务解释；已核实绑定、定义性计算、Event 准入及 Rule 要求仍是强制条件。未加限定的作用域指当前数据库与有效定义，不指全部历史。区分固有知识与当前请求筛选，并保留来源之间的分歧。属性谓词将直接业务承载者连接到承担属性角色的 Concept。存储在某对象的表中，不证明归属；关系不会传递属性归属。属性属于某个子类型时，优先采用有证据支持、实际适用的子类型，不编造普遍可用或独占归属。is_a 表示同类类别的包含，不一定是严格子类或直接子类；不适用额外知识准入测试。普通业务断言不会自动在类与子类之间转移：is_a(C,B) 与 r(B,p) 本身不能推出 r(C,p)，反方向也不能。这样的转移需要独立依据或明确允许的规则。共享父类既不意味着兄弟类互斥、重合，也不意味着穷尽覆盖。category_of 将属性类别/取值含义连接到其维度，不是连接到满足该类别的总体。属性槽位与其取值不是超类/子类。保持端点含义一致，绝不能用 description 否定谓词本身。

## 返回的 relation_metadata 补充说明

可选的 Concept 关系组：id、edges、description；至少包含两条同谓词、同方向的相邻边。不会隐式推理或展开。
