# Reconciliation Signals：检测原因、修复分支与操作边界

日期：2026-11-21（Asia/Shanghai）。状态：设计复阅稿；本文件没有修改运行时 Prompt、输出 schema 或后台 merge。

后续讨论已落地为[RelationMerger与Reconciliation v2](reconciliation-v2-implementation.md)：关系内容每批最多10组、无独立Assessment，Reconciliation保留8类Signal与独立Assessment。本页用于保留各信号的语义分析，实际代码与验证以[v2报告](../../output/reconciliation_v2_20261121/index.html)为准。

本稿区分现有检测行为与建议的新边界。Reconciliation 可以创建和修改有证据的业务节点，也可以重构局部关系；不能借此选择或消除已有 conflict、删除竞争知识，或通过普通副本绕过 conflict。

分类修订：不能把下面十二项都理解成“发现图错误”。其中有日常关系整合任务、泛化／补全机会，以及节点整合事务内的结构一致性与语义影响检查。后者不应常态化地把编译器可以解决的机械事项交给模型。

## 一、先归一化确定性重复，再生成语义检查 Signal

### 1. 节点合并产生的重复边

原图：

```text
E1: N1 --p--> N2
E2: N3 --p--> N4

已接受：N1/N3 -> A；N2/N4 -> B
```

重映射后两条边均成为 `A --p--> B`。若完整关系属性及作用域一致，应由代码保留一个边 ID、合并来源、记录旧边到保留边的精确映射，并同步引用，不交给 Agent 再判断是否重复。

可以任选的是代表 ID，不是任意丢弃另一条边的内容、来源或消费者知识。工程上应采用稳定选择策略，保证恢复与重跑一致。

### 2. 当前代码已经做了什么

- `integration/compiler.py::deduplicate_edges` 按 `edge_type + from_node_id + to_node_id + 完整 properties` 判重，不按边 ID 或来源判重。普通边保留先遇到的 ID，来源去重并集。
- `integration/patch.py` 的节点整合路径，以及 `integration/node_relations.py::sync_node_relations`，会在已接受映射后调用此函数。
- `properties.description` 也参与判重，所以不同措辞不会被自动认为等价；分支 scope 不同也不会直接判为重复。
- 当前 `parallel_assertions` 检测仍较宽：同一有向语义端点对存在多条边就触发，不要求谓词相同。

因此，当前并不是没有去重；但 description 往往不同，完整 properties 相等只能作为廉价的安全清理，不能承担主要的边内容整合职责。

建议把已重映射端点、谓词和 scope 一致的边先自动归入同一关系整合组，保留每条原 description、条件和来源，再进行语义整合。相同事实的不同措辞可生成一个完整描述；相容补充全部保留；条件、角色或竞争断言不同则保持区分。描述差异本身是正常整合输入，不是图错误。

不能简单忽略 description 后任选一条，因为条件或重要角色可能仅写在 description 中；也不能无差别拼接描述，将互不相容的断言包装成一个一致事实。候选归组可自动化，语义选择需要判断。可在同一 Writer/Assessment 局部任务中批量处理，不必另建一套多轮 Agent。

2026-11-21 用三个最小例子直接调用当前 `remap_edge -> deduplicate_edges -> inspection_signals`，结果如下。这里只验证函数行为，不是模型测试：

| 重映射后的两条边 | 剩余边 | 当前 parallel_assertions |
| --- | --- | --- |
| 同谓词、完整 properties 相同、来源不同 | 1，来源 case1/case2 均保留，E2→E1 | 不产生 |
| 同谓词，description 为两种同义措辞 | 2 | 产生 |
| organized_by 与 sponsored_by 两种角色 | 2 | 产生；这是当前触发范围过宽的例子，不代表业务错误 |

### 3. 建议的流程

```text
已接受的节点整合与版本映射
  -> 同步端点、显式引用及已有分支映射
  -> 确定性严格去重、来源并集、保存精确别名
  -> 自动构建需要内容整合的关系组
  -> 检查 metadata 等消费者，提供完整耦合材料
  -> 对具体关系整合、语义不确定性或泛化机会构造任务
  -> Writer 局部修复
  -> 真实候选编译与独立 Assessment
```

严格去重仅比较语义相关的规范化结构。已声明为集合的 scope 可按集合规范化；不能任意重排有位置含义的匹配组、条件或表达式。描述的语义等价需要判断，不能忽略 description 后任选内容。

活动任务的 before 一旦固定，不能在任务外静默归一化它。归一化应进入明确事务并保存映射。若重复边合并使 metadata 两成员坍缩为一成员，必须移交具体组合知识问题，不能静默删除组说明。

## 二、所有 Signal 的共同输入与验收

初始提供完成本轮判断所需的完整局部业务节点、完整解析 alternatives、真实关系、相关谓词契约和明确的关系集合完整性。原始证据默认给授权 ID，决定性疑点再读正文。

读取完整对象不代表授予任意写权限。每次修改关联具体 Signal、对象和结果；新增节点必须有独立业务含义、完整内容、来源及必要连接，不能创建占位节点来满足格式。

接受标准包括：目标问题有明确处理；原知识、条件、匹配方法、行为和来源保留；必要消费者兼容；没有相关回退。合法结构可以 keep。可选优化不应变成必须完成的义务。

固定 conflict 分支下可以独立证明的关系修复允许执行；需要选择、合并或消除分支才可决定的事项不在本轮裁决。合法待决与确定结构错误必须分开记录。

下面每类分别列出：检测事实、潜在原因、正常状态、修改分支、必要材料和验收。

## 三、八类结构／来源检测 Signal

### 1. abstract_predicate：实际关系仍使用抽象基谓词

**检测事实**：实际存活边使用抽象关系，例如 `has_attribute`。具体谓词继承该抽象谓词的类型声明本身不属于错误。

**为什么检查**：边可能只表达“有某属性”，没有准确区分业务角色；也可能主体、方向或属性承载对象安排错误。直接使用被禁止的抽象实例谓词属于确定结构问题，但具体原因尚需判断。

**正常状态**：使用准确的具体谓词；或者旧抽象边已经有保义后继且不再存活。

**修改分支**：

- 角色已明确：复用对应具体谓词；不存在合适契约时，声明有证据的完整新契约。
- 主体或方向有明确错误：修正端点；必要时修改角色说明。
- 原知识明确包含遗漏的业务主体或属性对象：可创建该节点并调整关系。
- 涉及未确认身份或需要 conflict 裁决：移交具体依赖，不能猜一个具体名字掩盖未知。

**例子**：`Patient --has_attribute--> Sex` 可以在角色明确时改为 `has_sex`。诊断存于 Examination 表，不足以证明诊断业务主体必须从患者改成检查记录。

**必要材料与验收**：完整端点含义、相关分支、原边与来源、候选谓词契约及受影响 metadata。关系需真正变得准确，不能只检查谓词名称是否更具体。

### 2. binding_contest：不同 Concept 竞争同一直接物理表示

**检测事实**：多个不同当前 Concept ID 直接 `grounded_on` 同一个物理 ID；同一 Concept 的重复边不是此类竞争。Metric 的物理输入不计入 Concept owner 集合。

**为什么检查**：当前政策要求同一物理 ID 全局最多一个直接 Concept owner。因此结构上需要处理，但原因可能是遗漏身份合并，也可能是实体／属性／表示层次混淆。

**正常状态**：直接 owner 唯一；不同 Concept 的有效 targets 可以重合，不要求每种匹配都拥有直接 grounding。不同分支不能豁免全局 owner 政策。

**修改分支**：

- 同一身份漏合并：提交明确的身份证据，经身份／节点整合流程确认后同步关系。
- 不同身份存在业务关系：保留各 Concept，调整不适当直接边，保留或补充真实 Concept 间关系。
- 明确遗漏属性或表示 Concept：可以创建，不能为了消除竞争任意制造共同 owner。
- 无法决定表示归属：保留记录并阻塞该结构问题，不随机选择、不凭来源数量投票。

**例子**：School 与 SchoolName 均绑定 `school.name`。若定义确认前者是实体、后者是名称属性，可保留 `SchoolName -> school.name`，建立或保留 `School -> SchoolName`。School 的原有效 targets 不因此删除。

**必要材料与验收**：物理端点、全部当前竞争 owner 与入边、完整定义及匹配方法、相关业务关系与消费者。唯一 owner 与知识保真必须同时满足，不能只以边数降为一条验收。

### 3. parallel_assertions：归一化后同一端点对仍有语义重叠候选

**现有检测事实**：同一有向语义端点对有多条边，不要求同谓词。A→B 与 B→A 不属于同一有向端点对。

**为什么检查**：节点身份合并后，原来不同来源的断言集中到同一端点，可能还有不同措辞的重复、互补知识、范围差异或错误角色。严格重复应先自动去除，剩余才需要判断。

**建议收窄触发**：同一端点对、同一谓词仍有内容差异的多条边，作为主要候选；跨谓词检查需已有契约或具体诊断提供重叠依据。不能仅因为 organized_by 与 sponsored_by 共存就生成修复任务。

**正常状态**：不同角色并存，或者相同角色在不同条件／分支成立。多条关系不是错误。

**修改分支**：

- 完整属性相同：代码自动去重，不消耗语义判断调用。
- 同义但措辞不同：确认事实与范围等价后整合说明和来源，同步引用。
- 同一事实相容互补：保留全部限定与知识，不把较弱来源解释成支持额外强断言。
- 不同角色或范围：保留多边，不压成宽泛 participant 等关系。
- 有明确事实错误：修正关系或相关节点说明；原断言包含遗漏业务对象时可补建。
- 端点身份误合并或需裁决竞争断言：移交，不改定义来迎合错误身份。

**例子**：Conference→University 的两条同内容 organized_by 自动去重；两条同义不同措辞 organized_by 可语义整合；organized_by 与 sponsored_by 默认保留。分支 a1/a2 的边不能仅因正文相同就清掉 scope。

**必要材料与验收**：完整端点、候选关系集合、范围、谓词契约、来源和 metadata 消费者。逐条旧断言均有保留方式；边数减少不是验收目标。

### 4. triangle：直接断言与两段路径共存

**检测事实**：A→B→C 与 A→C 同时存在；现有检测不证明谓词可组合，也不证明分支可共同成立。

**为什么检查**：可能是合并后留下的冗余显式断言，也可能是错误推导、错误方向或层级安排；但拓扑形状不能决定语义。

**正常状态**：直接边表达独立事实、消费者要求的直接输入，或者允许保留的显式层级。

**修改分支**：有明确推导许可与相同范围时，可检查可选简化；有据错误可修正端点、谓词或相关节点表述；原知识确有遗漏中间业务对象时可补建。不能为消除三角形造节点或造推导规则。

**例子**：M 的公式引用 X、Y，即使 X→Y，M→Y 也必须保留。Employee works_for Company 与 Company located_in City 不推出 Employee lives_in City。

**必要材料与验收**：三组完整关系、端点、契约、分支和消费者。若删直接边，必须在最终保留图中独立支持同范围原命题，并保留来源；不能循环自证。无法合法表达推导来源时保持直接边。

### 5. same_role_neighbors：同一角色关联多个不同对象

**检测事实**：Concept/Event 的同一出边谓词连接多个不同目标。

**为什么检查**：可能混淆了具体角色，或只保留了分散的边却丢失原有顺序、配对、组合含义；也可能只是正常多值关系。

**正常状态**：多个对象各自独立成立，无额外组合约束。例如 City served_by 多个 Airport。

**修改分支**：混淆角色时修具体谓词及必要节点说明；有明确遗漏角色对象时可创建；Concept 存在有据跨边命题时添加／修复 relation_metadata；邻居身份待确认时不自行合并。

**例子**：Transfer 的 sender/recipient 都被压成 participant，可据证澄清；Route 原知识明确先 A 后 B，应保留顺序。不能从边数组或 ID 顺序猜业务顺序。

**必要材料与验收**：起点、相关端点和该同谓词完整关系集合，原组合知识及相关 metadata。独立多值关系应可 keep；不能强制创建父节点或组说明。Event 不写 Concept 专属 metadata。

### 6. related_decisions：多个 Rule 共享作用对象

**检测事实**：至少两个 GenerationRule 通过 applies_to 指向共同语义对象。

**为什么检查**：对象整合可能让原来不同粒度或角色的规则接到一起，出现错误作用对象、遗漏前提或不相容行为；共享对象本身完全正常。

**正常状态**：独立决策共享同一对象，条件和行为各自完整。applies_to 不表示自动触发或沿层级继承。

**修改分支**：修 applies_to 对象、范围及相关引用／说明；有明确遗漏业务对象或计算结果时可创建并连接；修复有来源支持的条件表达遗漏。若需要合并 Rule 身份或实质整合独立行为，另立明确义务。

**例子**：要求按客户汇总后排名的规则被接到订单行粒度，应修复对象，必要时补建已有知识明确要求的客户汇总 Metric。患者去重与指标排名共享对象，不能强拼成一个动作。

**必要材料与验收**：各 Rule 完整 condition/action/reason、全部 applies_to 出边、对象完整含义和粒度。保留所有原独立行为及条件，不能只检查共享目标还在。

### 7. source_selection_variants：同一 Concept 的来源选择不同物理表示

**检测事实**：现有检测解析 SELECT 中可定位的列，与原 Concept targets 相交；映射到同一当前 Concept 的不同来源选择集合不同时触发。不是全 SQL 血缘分析。

**为什么检查**：整合可能丢失代码／名称等表示角色、匹配条件或消费者约束；不同选择也可能是正常的查询需求。

**正常状态**：多种完整匹配并存，标识、显示、计数等角色清楚；未 SELECT 某项不表示该项无效。

**修改分支**：恢复遗漏 targets/target_expressions，澄清角色和条件，修消费者引用；确有独立且遗漏的属性概念时可创建。有明确决策依据时才可补充选择规则，不能仅从投影差异生成全局策略。

**例子**：School 的 code/name 分别支持标识和显示，应保留两种匹配。COUNT(name) 与 COUNT(id) 可能受 NULL 和重复影响，不能自动互换。

**必要材料与验收**：当前完整匹配、各原来源节点完整表示、必要原题／完整 SQL、物理定位和实际消费者。每种有效表示及条件保留，不能合并外层 target groups 为联合匹配，也不能任意设置永久首选。

### 8. value_concepts：取值集合的维度概念与泛化／补全机会

**检测事实**：不同 Concept 分别直接绑定同一 Column 下的不同 DimensionValue；不证明值域完整、互斥或存在共同业务父类。

**为什么检查**：首先是正向结构补全机会，不默认原节点有错。多个语义取值分别绑定同一业务列时，应检查该列是否已有表达业务维度的 Concept，以及维度与取值之间的语义关系是否完整；还可能存在可泛化的对象子集。仅在实际混淆层次时才属于错误修复。

**理想状态**：业务维度有清楚的语义表示；各取值或对象子集角色清楚，匹配和关系完整。缺失且业务含义明确时，应补齐维度 Concept；这不等于为所有数据库列机械创建 Concept，也不等于给所有取值建立 is_a 父类。

**修改分支**：优先复用已有维度 Concept，确实缺失时根据列业务定义、现有节点与来源创建；建立有明确契约的“取值属于维度”等关系。若现有节点实际指对象子集，可补充有据共同对象概念和 is_a，并另行表达其属性条件。可修改名称、定义、targets 和角色以澄清层次，不能丢已有条件。物理目录只读。

**例子**：Gender Concept 直接表示 SEX Column；Female/Male 取值 Concept 分别绑定物理 F/M，并以有据的具体关系关联 Gender。物理 F/M 仍通过 value_of 关联 SEX Column。若原节点是 FemalePatient/MalePatient，则它们是患者子集，不能直接冒充属性取值；可在有完整定义与匹配依据时补 Patient 和性别关系。仅见 F/M 不得断言二元穷尽。

**必要材料与验收**：Column/Value 真实归属、完整 Concept 含义与匹配、相关关系；主张全域或互斥时另需完整依据。保留分类条件，不通过把多条 Value 边改绑同一 Column 来丢条件或制造 owner 竞争。

## 四、节点整合事务内的三类耦合检查与移交载体

这些名字不是八类日常扫描 Signal 的同类项目。当前 `sync_node_relations` 在节点整合候选接受前检查它们，`task_runner` 可调用关系协调完成同一候选的耦合修复；它们不是宣称抽取图已经合法提交之后又无故发现旧错误。

两个输入分别合法，不保证任意合并变换后仍合法。但机械同步是编译器义务，不能把 ID 更新、已有明确映射或确定性结构生成包装成模型任务。只有新整合确实产生需要语义判断的差异时才移交。最终应作为同一事务接受，不能先接受损坏节点结果再要求下游补救。

### 9. metric_direct_inputs：实际公式与直接输入关系不一致

**触发事实**：某个 Metric 分支的 refs 与直接 depends_on/grounded_on 集合存在 missing/stale，来自具体校验诊断。

**为什么是问题**：消费者依赖图不能准确表达该公式的直接输入，可能漏算、错误继承或将一般业务关联当作计算操作数。

**正常状态**：逐分支直接集合与 refs 一致；同一 refs 在表达式多次出现无需重复建边。

**修改分支**：补缺边，修类型、端点、scope、引用 ID 和明确遗漏的表示；保留其他有效业务事实的真实后继；已有知识明确包含缺失操作数时可补建。算术口径本身需重选时，应追加具体内容修复义务，不能仅为对齐边改公式。

**代码与模型的分工**：已确认别名映射导致的 refs／端点更新应自动同步。明确 refs 下的结构缺失应由一致性维护器生成或报编译缺陷，不常态化询问模型。若旧边还承载独立业务含义、操作数等价尚未确认，才需要语义判断。真实 Metric 回归中，两个原 Metric 分别引用 C266/C204，合并草稿选择 C266 却继承两条边；这应在合并同一事务内明确操作数与关系去向，不能用一句“概念等价”代替已确认映射。

**例子**：a1 refs=X、a2 refs=Y，则分别修 M→X[a1]、M→Y[a2]，不选择哪一公式正确。X/Y 已确认同身份时同步 refs 与边。

**必要材料与验收**：完整前后公式、全部相关分支、全部直接输入、真实别名及来源。逐分支集合一致且原计算、单位、粒度、DISTINCT/NULL 行为保留；间接路径不能替代直接输入。

### 10. concept_metadata_repair：关系组合命题的表示失效

**触发事实**：metadata 引用缺失／退休边，去重后成员不足，成员谓词／方向／分支不相容，或修改有丢组合知识风险。

**为什么是问题**：metadata 不只是 ID 列表，它可能承载顺序、配对、覆盖等原始命题。机械重映射可以修 ID，也可能改变整组含义。

**正常状态**：至少两条不同真实相邻边，同谓词同相对方向且可共同成立，组级知识仍被准确表达。

**修改分支**：精确等价映射可自动修引用；有语义影响时修成员和说明、调整相关关系；原知识确有独立业务对象而当前未表达时可创建并承接。只有组级知识已在合法后继中完整保留才可撤组。

**代码与模型的分工**：仅 ID rename 后未同步引用属于编译器责任，不应成为常规模型修复任务。边整合导致组成员坍缩或角色变化则是新语义后果，要将旧组命题和最终成员一起核查。机械去重应事先检查消费者，不能先无条件去重再把组损坏视为上游已接受结果。此前 metadata_alias 小测有意注入未同步 ID，只证明修复路径可测试，不证明原 case graphs 存在此错误。

**例子**：E1/E2 去重成 E，不能变成 [E,E]，也不能直接删“先A后B”的说明。精确 rename 与语义后继必须区别。

**必要材料与验收**：旧组完整命题、全部旧成员、当前后继、相关分支和消费者。不能造假边凑两条，也不能用格式通过代替组合知识保留。

### 11. target_alternative_scope：原关系所依赖的终点含义发生版本变化

**触发事实**：节点整合后，原关系终点被重写或映射为多个 alternatives，无法仅凭 ID 证明原断言仍适用。

**为什么是问题**：同一节点 ID 可能承载不同完整竞争版本；原边不一定对所有版本都成立。alternative_ids 只能选择起点版本，不能选择终点版本。

**正常状态**：关系对目标身份的所有相关版本都成立；或已有合法保义后继完整支持原命题与消费者。

**修改分支**：核实后可 keep；有据时修关系、起点引用／说明／scope；来源确有另一个独立业务对象时可创建并正确连接。需要选择目标分支或消除 conflict 才能决定时，记录依赖或表示能力问题。

**触发收窄**：这是目标语义变化的影响检查，不应把所有入边或所有措辞变化当作错误。当前 `_same_target_versions` 以完整内容精确比较作保守判定，描述差异也可能触发移交；新设计应利用明确的版本保义映射和关系实际依赖的差异，缩小到有具体疑点的消费者。它不授权裁决 conflict。

**例子**：Student enrolled_at School 若各版本只改变匹配表示且都仍指该学校身份，可以保留。利润率只适用含税销售额版本时，不能把该目标分支 ID 写入起点边的 alternative_ids。

**必要材料与验收**：原目标完整内容、当前全部相关版本、原关系及受影响消费者、真实映射。不能通过普通化 conflict、复制某分支为假新身份或造 target_alternative_id 关闭义务。

### 12. node_relation_followup：来自节点阶段的具体未闭合事项

**触发事实**：上游提供稳定义务 ID、原记录、问题、required_outcome 及映射。它是移交载体，不是拥有全部权限的通用语义模式。

**为什么检查**：节点内容正确整合不等于其外部关系已经保义；被删旧 ID、通过节点评估或旧诊断不再出现，都不能独立证明关系义务完成。

**正常状态**：当前关系或明确后继已完整满足原要求，可以独立确认 keep，不必重复修改。

**修改分支**：按具体问题分派至前述类别，限定可以修改的节点字段、关系和必要新节点；已接受的机械事项由代码完成。移交描述不足时由 Controller 补齐，不能让模型猜“让图合理”是什么意思。

**例子**：上游已经产生完整汇总 Metric，但留下补齐直接输入的义务，可以补其边；不能因此重新改变汇总口径。

**必要材料与验收**：完整原要求、版本绑定、原关系与当前后继、范围、来源及消费者。逐项闭合或明确合法延后，不因安全 no-op 提交就清空未完成义务。

## 五、后续实现与小范围验收要求

1. 严格重复边先自动归一化，保留来源、精确映射和消费者知识；不进入普通语义去重任务。
2. parallel_assertions 不再将所有不同谓词的正常多角色关系当作修复任务。
3. 弱结构模式只提供检查线索；不能要求消除正常多值、三角形或共享对象。可缓存 keep，相关事实未变化不反复调用。
4. 每项变更绑定具体 Signal 与对象，不把多个 Signal 的存在解释为任意修改权限。
5. Assessment 首包准备完整必要内容；节点正文变化与关系变化分别展示；完整性和全局反例由 Controller 明确提供。
6. 保留节点创建／修改能力，同时禁止通过复制、退休、覆盖等方式裁决或消除 conflict。
7. 区分安全接受、事项完成、合法保持、非阻塞延后与结构阻塞，持久化依赖且不在恢复时无条件重跑。
8. 至少测试：双端点合并后 exact duplicate 自动消除；同义不同措辞保留为候选；不同角色默认保留；scope 差异不被清除；metadata 坍缩不丢知识；固定分支 Metric 可修边；目标分支不可伪表示；正常多值／三角形／共享 Rule 不强制改图。
