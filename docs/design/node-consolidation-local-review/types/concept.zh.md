# 本组类型 Guidance：Concept

## 1. 整合目标与边界
- **整合对象**：同一业务对象、类别、属性或术语的名称、含义与物理匹配方法。
- **核心边界**：保持原有业务边界；不因共享数据库列而扩大身份，也不把“名称表示”与“名称属性”混为一谈。

## 2. 字段填写规范

| 字段 | 普通结果与每个 `alternative` 的填写要求 |
| --- | --- |
| `name` / `aliases` | 同义名称归并；不同表示角色需在定义中说明，不得假装业务角色可互换 |
| `description` | 简洁说明业务指代与必要范围；不用“多个相关字段”掩盖角色差异 |
| `properties.definition` | 当本轮 schema 存在该字段且有必要时，整合完整定义与区分条件；不得否定任一仍有效的输入定义 |
| `properties.targets` | 非空二维 ID 列表，每个内层列表是一套完整联合匹配方法；不同外层组不是默认 `SELECT` 列清单，也不自动代表 `UNION`、`JOIN` 或任意互换 |
| `properties.target_expressions` | 可选对象；键为 `targets` 当前外层下标字符串（如 `"0"`、`"1"`），值为对应组必要的完整匹配条件/关联表达式 |
| `properties.mapping_type` | 可选字符串；相容时归一，不改为数组；有实质差异时保留在定义或分支中 |
| `properties.relation_metadata` | 可选的既有相邻边分组；须遵守下方结构与范围限制，不能替代真实边 |

## 3. `targets` 与 `target_expressions` 联动规则
- **端点与格式**：组内均为本轮允许的真实物理端点 ID，非空且不重复；禁止用自然语言列名代替 ID。端点允许的类型以本轮 schema/端点契约为准，不套用旧阶段字段格式或另建 target 对象。
- **组粒度与去重**：保留相容的完整匹配组；除非原知识本来要求联合匹配，否则不同组不拼入同一内层列表。判重需同时比对组内端点与匹配表达式；同端点但条件不同不是简单重复，同条件是否等价也须有依据。
- **下标同步**：组重排、删重或合并后，必须重新计算 `target_expressions` 下标；键只能是 `"0"`、`"1"` 等有效下标字符串，不能使用 group ID、列 ID 或整数键。
- **表达式与边约束**：保留原有关联/条件，使用目录中的 SQL 表列名或表达式中实际声明的别名，不使用 graph ID 作 SQL 标识符，也不引用匹配组外的物理列。不能删掉条件后宣称等价，也不能把条件只写在 `explanation` 中。`targets` 不会自动创建 `grounded_on`（不是“每组补一条绑定边”的任务）；有效旧关系应保留，新边须明确且有来源。

### 示例：相容合并
“School”成员 A 通过学校代码表示，成员 B 通过学校名称表示，且明确指代同一学校实体：

```json
{
  "name": "School",
  "description": "学校实体，可通过学校代码或学校名称表示；二者的标识与显示角色分别保留。",
  "aliases": ["学校"],
  "tags": [],
  "properties": {
    "definition": "学校业务实体；代码表示与名称表示并不意味着名称具有现实唯一性，或二者可作为等价计数操作数。",
    "targets": [["column.schools.code"], ["column.schools.name"]]
  }
}
```

- 切勿改为 `[["column.schools.code", "column.schools.name"]]`，也切勿把节点统一改名为“学校名称”。实际 ID 与字段须以本轮任务为准。

### 示例：带条件的组重排
若输入组 A 为 `targets=[[column.a]]`、`target_expressions={"0":"t.a IS NOT NULL"}`，输入组 B 目标为 `column.b`；当输出将 B 排前、A 排后时，A 的键必须更新为 `"1"`，不得将旧键 `"0"` 原样带入并错误约束 B。

## 4. `definition`、属性与泛化（Generalize）
- **同义与互补合并**：定义同义或相容补充时可重写为完整统一定义（如“账户注册时记录的日期”与“用于确定注册时间范围的日期”可合并，无需逐句重复）。
- **拒绝虚假泛化**：
  - “学校代码表示”与“学校名称表示”可在同一 `Concept` 中保留各自角色，无需新增泛化占位符替代两组 `targets`。
  - 不得将“已完成订单”泛化为“具有某状态的订单”并删掉完成状态及原条件；固定业务定义不是偶然 query 参数。
- **互斥匹配方案**：`Concept` 目前没有通用的请求参数选择器；若不同请求必须在两个互斥匹配方案中二选一，不可仅写“按上下文选择”做扁平并集。需读取来源确认，仅在现有定义/表达式能准确表达时合并，否则保留真实竞争分支或报告缺少前提。

## 5. `relation_metadata` 规范
每项须严格遵循结构：

```json
{
  "id": "...",
  "edges": ["edge-1", "edge-2"],
  "description": "完整组合关系含义"
}
```

- 同一节点内 `id` 不重复；`edges` 包含至少两个不重复的真实相邻边 ID。
- 组内边须同谓词、相对 owner 同方向，且分支范围能够共同成立。
- 不分组互斥分支中的关系，不引用已删除且无后继的边；边合并后的引用映射由代码处理，但语义组合仍需有效。
- 单条边的角色与条件应写入边自身的 `description`，不另造 `relation_metadata` 对象替代。

## 6. 保留 `alternatives` 的条件
- 当重叠范围内对同一 `Concept` 的定义或完整匹配解释不兼容时，须保留完整分支。
- 每个分支各自具备 `name`、`description`、`aliases`、`tags` 与完整 `properties`，并保留各自的匹配组、表达式与关系范围。
- 不得只给出一个不同的 `target` 片段，也不得将另一分支独有的别名、条件或来源无条件复制过来。
