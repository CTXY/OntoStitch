# 本组类型 Guidance：Metric

## 1. 整合目标与边界
- **整合对象**：同一业务数量的完整计算口径，由公式、操作数含义、粒度、总体、单位、`NULL`/零值行为与计算次序共同决定。
- **核心边界**：
  - 名称相近不能证明计算等价；不得重新审计未改变的已接受来源是否应当成为 `Metric`。
  - 若实际上分别指两种不同的业务指标，给出身份反例交回 `Identity`。

## 2. 字段填写规范
- **`name` / `aliases`**：数量的规范名称与同义词；不得把不同口径仅以别名方式混同。
- **`description`**：保留总体、单位、粒度与必要条件；没有独立 `unit`/`grain` 字段时在此或 `pattern` 中表达，不新增未声明属性。
- **`properties.expression`**：必填对象，仅含 `expr` 与 `refs`：
  - `expr` 为非空计算表达式（非完整 `SELECT` 查询），使用 `${amount}` 等占位符；公式中的占位符集合必须与 `refs` 的键完全一致，不得使用未知节点、遗漏引用或写入多余 `refs` 键。
  - `refs` 为占位符名称到真实节点 ID 的映射。
  - **计算校验与真实性**：计算校验会拒绝裸列引用、只做 `CAST` 或仅包裹 `+0`、`-0`、`*1`、`/1` 的恒等表达式；不得为通过校验给裸列加此类包装。新候选须保留来源本有的真实计算；若历史输入本身与本轮契约不兼容，报告输入/迁移问题，不编造 `SUM` 等计算修补。
- **`properties.pattern`**：可选自然语言计算模式，必须与 `expression` 同义；不得用它补回公式中被删除的 `SUM`、`DISTINCT` 或条件。
- **`properties.sql_generation_plans`**：可选完整计划列表，每项仅含 `id`、`application`、`steps`：
  - `id`：匹配 `[A-Za-z][A-Za-z0-9_]{0,99}` 且节点内不重复。
  - `application`：非空文本，去首尾空白后最多 500 字符。
  - `steps`：1–8 条非空文本，每条去首尾空白后最多 600 字符。

### 完整内容示例：相容合并
当输入均定义同一订单支付总额、公式一致，且一份提供中文名、另一份补充“已确认范围内订单金额求和”说明时，可合并为如下完整 `NodeContent`（具体物理引用须存在于本轮目录）：

```json
{
  "name": "订单支付总额",
  "description": "在来源确认的同一订单范围内，对支付金额求和，保留原 SUM 行为与订单粒度。",
  "aliases": ["Total order payments"],
  "tags": ["支付金额"],
  "properties": {
    "expression": {"expr": "SUM(${amount})", "refs": {"amount": "column.orders.amount"}},
    "pattern": "对原范围内订单的支付金额求和。"
  }
}
```

- 此为 `NodeContent`，不包含 owner ID 或 evidence 字典；Writer 提交时放入 `integrate_groups` 的 `content`，并按公开契约填写成员与来源路由（`Assessment` 只比较实际内容，不提交该结构）。不得用此示例为原本无此计算的输入新增求和。

## 3. 相容整合与泛化（Generalize）
- **互补与多计划共存**：同一完整公式的互补解释、同义名称与等价计划可整合；比较前须沿已提供的必要依赖理解操作数，不得把原派生量替换为无相同计算含义的裸列。多种实现计划仅在各自适用条件与完整行为明确时可共存，不得把不相容公式拼成“通用公式”。
- **时间窗与请求参数边界**：
  - 仅当输入为请求时间窗差异且该窗口不属于固定指标定义时，可保留明确的窗口参数含义；不得把固定口径、固有阈值或单位缩放变成任意参数。
  - 请求的排序、展示或分组选项可在确有依据时参数化，但指标自身的计算、行粒度或过滤不得借此丢弃。
  - `Metric` 的 `${key}` 是**节点引用**，非通用参数系统；不得将请求值绑定到不存在的 node ID，也不要在 `expression` 对象中新增 `parameters`。

## 4. 不兼容口径与分支处理
- **典型不等价情形**：
  - `SUM(price / amount)` 不可改为 `SUM(price) / SUM(amount)`；`SUM` 不可因 `name` 含“平均”而改成 `AVG`。
  - 行数与去重实体数、含税与未税、不同 `NULL`/零值处理、不同聚合顺序均可能构成实质差异，不可仅合并说明文字。
- **保留完整 `alternatives`**：已证实同一范围下不兼容时，保留完整分支；每个分支须具备各自完整的 `expression`、`refs`、说明、适用计划与依赖边，不得跨分支取公式片段或混用 `refs`。
- **缺失前提处理**：若仅缺少唯一性、粒度或操作数定义，先读取相关 `evidence`；无法确定时报告缺少前提，不得擅自修正原始计算。

### 示例：不兼容口径 vs 身份差异
两份来源对同一“平均成交单价”分别承诺 `SUM(price)/COUNT(*)` 与 `SUM(price*quantity)/SUM(quantity)`：若确认同范围口径不同，应分别保留完整版本与 `refs`，不能写成“按适当方式取平均”；若实为两种不同业务指标，则给出身份反例交回 `Identity`。
