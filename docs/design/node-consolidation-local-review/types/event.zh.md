# 本组类型 Guidance：Event

## 1. 整合目标与边界
- **整合对象**：同一业务发生**类型**及其角色、范围和关联（而非某次发生的实例记录），涵盖“发生了什么、谁参与、何种时间/地点/对象角色、已知粒度”。
- **核心边界**：
  - 不得仅凭相同日期列、参与者列、`JOIN` 路径或相似动词判定事件类型相同。
  - 区分不同发生类型（如“申请”与“批准”即使共享对象和日期表，也可能是不同发生类型）；若实为不同类型，给出具体反例交回 `Identity`，不用 `alternatives` 掩盖身份错误。

## 2. 字段填写规范
- **`name` / `aliases`**：同一事件类型的规范名称与有依据的同义名称；不得把角色不同的事件名称混为同义词。
- **`description`**：简明概括事件含义与必要角色。
- **`properties.definition`**：**必填非空文本**；完整说明业务发生、范围与已知粒度。
- **`properties.targets`**：可选的完整匹配分组；若存在，须遵守二维真实物理 ID 格式，组内非空且不重复，不把不同匹配方法拼成一个联合组；组重排时须同步重建 `target_expressions` 索引，且外层相同组与相同表达式的完整组合不得重复。
- **`properties.target_expressions`**：可选对象，以有效 `targets` 下标字符串（如 `"0"`、`"1"`）为键，值为非空完整识别条件/关联表达式；键须规范且不越界；若省略 `targets` 或 `targets` 为空（`[]`），不得遗留任何表达式条目。
- **关系与 `targets` 边界**：事件可通过有效业务关系连接已绑定 `Concept`；不得为了字段覆盖而编造 `targets` 或“日期不为空就表示事件发生”的条件。

### 完整内容示例：互补角色说明
当两份来源明确指同一“客户提交订单”事件类型——一份说明提交主体是客户，另一份说明作用对象是订单，且原有 `relations` 明确属于同一发生——可整合为：

```json
{
  "name": "订单提交",
  "description": "客户向系统提交订单的业务发生类型，以提交的订单为粒度，保留客户主体与订单对象的关联。",
  "aliases": ["下单提交"],
  "tags": ["订单流程"],
  "properties": {
    "definition": "客户提交一份订单；客户是提交主体，订单是作用对象，原来源确认二者属于同一提交发生。"
  }
}
```

- 此处未编造物理匹配；原有角色关系继续保留在 `relations` 中，不因 `NodeContent` 省略可选 `targets` 而删除。若同一类型另有来源支持的相容匹配组，应照实保留，不可照抄本例删去。

## 3. 相容整合与泛化（Generalize）
- **同义与互补保留**：对同一事件类型的同义名称、互补角色说明及相容物理匹配方式可整合，保留角色与同一发生的配对关系。
- **请求参数 vs 固定范围**：
  - 若某次请求指定的参与者或时间窗仅作为筛选实例的参数，可在说明中保留其角色；不得把事件类型的必要参与含义或固定范围弱化为“任意事件”。
  - 若查询仅一次筛选客户 A、另一次筛选客户 B，不应将“提交订单”绑定为两个事件类型，可保留共同事件类型与参与者角色，具体筛选值由请求决定；但若“客户 A”本为固定业务范围，则不得擅自泛化为任意客户。

## 4. 冲突、缺失前提与关系处理
- **保留完整 `alternatives`**：同一事件类型在重叠范围下存在不兼容角色或发生定义时，保留完整分支；各分支须具备各自完整的 `definition`、`targets`/表达式与适用关系，不得跨分支混用参与者配对与发生条件；分支专属边须使用准确的 `alternative_ids`。
- **缺失前提处理**：若原材料仅能支持某个时间属性，不得通过泛化编造完整事件发生判据；必要关联不足时报告缺少前提，不凭邻近字段补全说明。
