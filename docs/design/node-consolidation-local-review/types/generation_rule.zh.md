# 本组类型 Guidance：GenerationRule

## 1. 整合目标与边界
- **整合对象**：同一个可复用的 SQL 生成决策，涵盖生成结果要求、涉及对象/角色、适用条件与完整行为。
- **核心边界**：
  - 不凭名称、`triggers` 或 `operation_intents` 标签判断等价；不同 `action` 文本可能是等价实现，同一 Gold SQL 中的两个操作也可能是独立义务。
  - 不重新审计已接受来源的原子性；遇到具体身份反例应交回 `Identity`。

## 2. 字段填写规范

| 字段 | 普通结果与每个 `alternative` 的填写要求 |
| --- | --- |
| `name` / `aliases` | 选用代表生成决策的稳定名称，同义名称放入 `aliases`；不以单次 case 常量命名 |
| `description` | 简洁说明决策及范围，不复述整条来源查询 |
| `properties.condition` | **必填非空字符串**；执行决策前可识别的业务/请求条件，不得用 case ID 作分支条件 |
| `properties.action` | **必填非空字符串**；完整、可实现的生成行为，保留操作数、参数绑定、计算次序与边界，必要时提供 SQL 模式；不为凑清单制造模板 |
| `properties.reason` | **必填非空字符串**；保留有依据的决策理由、结果差别或失败规避；字段名固定为 `reason`，不是 `rationale` |
| `properties.operation_intents` | 可选字符串列表；去重并合并相容标签；字段名为复数 `operation_intents`，不是 `intent` 或 `operation_intent`；标签不能替代 `action` |
| `properties.triggers` | **必填对象**；仅含 `question`、`sql` 两分支，至少包含一个有效检索信号 |

### `triggers` 结构与约束
```json
{
  "question": {"phrases": ["原始 Question 中有依据的短语"]},
  "sql": {"columns": [], "operations": []}
}
```

- `question` 下仅允许 `phrases`；`sql` 下仅允许 `columns`、`operations`；值为非空字符串列表，列表可为空，但三个列表**不能全空**。
- 不得改为自由文本、字符串数组，或新增 `keywords` 等字段；合并信号时须去重，不捏造原问题未出现的短语，SQL 修复信号仅保留来源中真实存在的用途。
- `triggers` 用于检索而非执行前提；归并同一规则的有效检索信号后，仍须由 `condition`/`action` 限定真实适用范围，不能因某 trigger 命中而同时执行全部条件分支。

## 3. 相容补充、等价实现与泛化（Generalize）
- **相容合并与等价实现**：
  - 同一生成决策的互补操作数含义、必要关联、`NULL` 行为或等价 SQL 模式可整合为完整 `action`。
  - SQL 写法不同未必冲突（如 `x > 5` 与 `5 < x` 可等价）；窗口函数与子查询仅在输入粒度、`NULL`、并列与输出形态均相同时可视为等价实现。
  - 来源仅要求排序时不得借整合新增 `COUNT DISTINCT`；来源已有计算时不得写“交由上游处理”而丢弃计算；互补实现应写成带明确前提的完整模式，而非把多个来源查询复制成无关 case 列表。
- **何时可参数化**：
  - 仅当来源明确支持请求提供的参数（如 `K`、比较阈值、时间区间、排序度量、方向或被筛选实体）且同一行为适用于该取值域时，才可在 `condition`/`action` 中说明参数角色与绑定方式；不得新增 schema 不存在的 `parameters` 字段。
  - 仅有两个来源用了不同数字，不足以推出任意取值均合法（如不能从 `3`、`5` 外推出所有正整数）；需保留来源实际支持的范围。
  - 规则中的 `K` 为自然语言参数说明，非 `Metric` 的 `${key}` 引用，也不要求直接把 `<K>` 当作可执行 SQL 常量；若提供 SQL 模式，需明确生成时的替换方式。

### 完整内容示例：可泛化的请求参数 `K`
假设成员 A 按请求选前 3 个客户，成员 B 选前 5 个客户，排序度量、每客户粒度、方向与并列处理均一致，且 `K` 来自请求并明确支持取值域与并列策略：

```json
{
  "name": "按请求选取前 K 个客户",
  "description": "按既定客户销售额降序选择请求数量的客户，以客户 ID 升序打破销售额并列。",
  "aliases": [],
  "tags": ["客户排名"],
  "properties": {
    "condition": "请求基于既定每客户销售额选择前 K 个客户，K 是请求给出的正整数；原来源均采用客户 ID 打破并列。",
    "action": "在每客户一行的既定销售额结果上，按销售额降序、客户 ID 升序排序，限制为请求 K 行；生成 SQL 时用请求中的正整数替换 K，保留来源已有的口径与 NULL 行为。",
    "reason": "保持选择客户这一结果义务；K=3 与 K=5 均可还原原行为，不改成仅求最大销售额。",
    "operation_intents": ["top_k_selection"],
    "triggers": {"question": {"phrases": ["前"]}, "sql": {"columns": [], "operations": []}}
  }
}
```

- 上例仅为 `content`，成员、来源路由与必要边操作须按公共输出契约填写；不得作为所有排名规则的默认策略。

### 不能靠参数化消除的差异
- **`COUNT(*)` 与 `COUNT(DISTINCT patient_id)`**：计数对象/去重语义不同，不能简化为 `COUNT(<operand>)`；需证明唯一性与原粒度，或保留竞争版本。
- **`RANK`、`DENSE_RANK` 与 `LIMIT`**：并列时返回结果可能不同，不能仅泛化为“按某方式取前 K”；证明唯一排序且原行为等价可合并，证实同范围行为不同则保留 `alternatives`，唯一性或并列前提未知时先读 `evidence` 或报告缺少前提，不默认冲突。
- **固定业务阈值与 JOIN 策略**：定义类别边界的固定阈值（如“发热”固定阈值）不能变成任意请求参数；先聚合再 `JOIN` 的行为不能泛化成任意 `JOIN`，不得引入明细扇出、遗漏空匹配对象或把 `INNER JOIN` 变为无条件要求。

## 4. 条件变体与冲突处理
- **明确条件变体**：若“包含未匹配对象”与“只要有匹配对象”等请求条件在来源中明确，且 `action` 完整保留各自 `JOIN` 策略，可整合为带明确条件的生成规则；条件须在决策前可识别，不得写成“当应使用版本 A 时使用 A”，也不得凭来源 ID 或标签捏造范围。
- **保留完整 `alternatives`**：同一范围下不兼容的选择须保留完整分支，各分支具备各自的 `condition`、`action`、`reason`、`triggers`、`operation_intents` 与必要依赖关系，不得跨分支混用 `action` 与 `reason`。
- **分支演变**：旧 `alternatives` 不必永久保留原数量，等价重复可去重、相容版本可整合，但每份有依据的不同义务须通过来源路由与最终内容完整保留。
