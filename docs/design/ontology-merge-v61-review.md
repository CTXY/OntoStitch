# Ontology merge v61：多角度设计审查与修订建议

> 完整执行方案已汇总为 [v62 design](ontology-merge-v62-design.md)，强化了“业务身份差异与同身份实现/口径差异分开处理”的边界，并逐步定义代码与 Agent 职责。本文保留审查过程与问题依据。

日期：2026-11-07。本文针对最新对话方案做设计审查，不表示生产实现已修改或真实合并实验通过。v60 是历史草案；最新要求取消 U 作为正常输出，不以保守 uncertain 退出为常规策略，并把共同含义—差异解释—整合重构作为核心。

## 1. 审查范围与结论边界

三个 subagent 分别审查：语义身份与差异判定；局部边界与增量迭代；整体可执行性及代码接口。主要方法是读取现有实现、构造反例、检查判断是否能落实到具体读写与审查动作。

已有合理基础：节点与关系联合解释、物理锚点只作候选信号、保留 shared/differences/explanation 分析、局部事务、独立 Assessment、不要求全图 DAG、不追求唯一最简图。

本轮重点发现：部分判断仍依赖模型自行声称完成；差异分类与最终候选之间缺少组合约束；实现接口仍限制于单节点；取消正常 U 后，纯关系真实冲突的图内表达尚未闭合。因此不能宣称完整算法已审查通过并支持所有输入。

## 2. 核心语义规则需要如何收紧

### 2.1 身份与兼容性分开判断，但允许相互修正

Identity 比较业务所指、量或独立生成义务，不要求计算实现、动作、邻域预先完全兼容。否则同一指标的错误/竞争实现会被提前拆成两个 identity。也不能只凭名称相同就把不同统计对象放入同组。

关系用于召回、解释对象角色和发现反证，不是自动同义规则。相同关系类型不足；需看方向、关系含义、相邻对象与适用范围。邻域缺项不是否定证据。待确认的多个对应可以联合评审，但不能仅相互支持形成循环自证。

相同主体可通过同类关系连接多个不同对象。例如 School 的官网和招生入口均可经 has_website 连接；除非契约与来源支持，不得把该关系默认当作单值函数，从而推出两个目标相同。

同义合并应保持原有指称，不能把 School 和 University 概括成 Educational institution 后称为同一 identity。

### 2.2 互补不意味着节点必须合并

同身份的互补信息可以整合；不同、可独立应用的义务通常保留不同节点。一个 SQL 同时要求“去除重复实体”和“处理 NULL 分母”，不能因为二者兼容就形成一个复合 GenerationRule。

分析可以发现互补关系，修改动作仍受 Concept/Metric 的 NL 最小化、Rule 的 action 最小化约束。

### 2.3 差异逐项分析，结果按完整语义构造

分子、分母、总体、单位、过滤条件与依赖有组合关系；Rule 的 condition/action/作用对象也有组合关系。不能把每个差异分别判为可合并，再任意交叉组合字段。

例如输入是 `returned_units / sold_units` 和 `orders_with_returns / all_orders`，即使它们同属一个竞争指标定义，也不能生成 `returned_units / all_orders`。每个发布候选必须是一份完整且自洽的定义，其组合要有来源或被审查通过的语义解释支持。

这不要求增加可执行“语义耦合图”：保持现有完整候选，并要求 Assessment 检查解释是否在整体公式/动作/关系中成立即可。

### 2.4 条件化解释必须真的解释行为差异

条件应当在选择实现之前能够从请求、业务上下文或相关数据约束中判断；不能写成“当适合 F1 时使用 F1”。条件不得使用 case ID、源图 ID、被选择的公式名字，或无法解释差异的偶然常量。

需同时检查：

1. 条件与行为差异有具体语义联系；共同出现不是理由。
2. 代入各来源上下文后，能够重建其要求。
3. 分支重叠时，行为是否兼容，或是否有支持的优先规则。
4. 未被已有分支覆盖的情况，不得无依据生成 else 行为。

不要求分支覆盖所有可能请求，不因此强造通用 selector/参数 DSL；所有条件必须进入真实定义，不能只留在 analysis.applies_when。

### 2.5 真实冲突比较要求，不只比较实现输出

在可比较的指称、角色、条件和量词下，两侧来源支持的要求不能同时成立，且没有合理条件解释或明确错误可修正，才确认真实竞争。

“两个 SQL 的结果不同”不充分。例如请求允许从并列最高对象中任取一条，按 ID 升序与降序各取一条可能都满足请求；不能把实现选择提升为相互矛盾的业务政策。

可用允许结果的视角帮助判断：对同一输入 x，若两个实现结果都落在任务允许的结果集合 A(x)，观察到结果不同不足以推出冲突。更一般地，需比较动作施加的义务/限制，而不是逐字符比较 SQL。该视角不要求将所有业务关系编码成集合求解器。

即使当前数据库没有 ties、两个实现恰好输出相同，明确的相反政策也可能仍不兼容。无 ties 的一次回放不能替代对要求的比较。

固定业务值不能一律参数化。例如某术语本身由一个指定状态值定义，该值是含义的一部分；请求中的年份可能只是调用参数。判断依据是改变该值是否改变节点原本所指或义务，而非它是否多次出现在样本中。

### 2.6 支持、纠错与 source coverage

保留的是来源支持的要求，不是原始抽取中的每个字。抽取内容若被原始 NLQ/SQL 或明确契约驳倒，允许修正，并说明去向/原因。单个 SQL 未用到某条知识，不足以证明它错误。

Gold SQL 是当前任务行为的重要证据，但它的具体执行选择不能自动升级为永久业务限制；NLQ/SQL 自身互相矛盾时，不应通过改写 ontology 隐藏问题。

现有 shared.md 和 coverage 的表述需统一到这个边界，避免“保留全部原始计算”与“有据纠错”相互冲突。

## 3. 局部范围不能由 DecisionReady 自我认证

### 3.1 代码给出必需材料，Agent 请求额外读取

代码生成与当前决策相关的最小材料清单，而不是递归扩展整个依赖闭包：

- 本次实际比较的候选定义完整可读；大内容可分页。
- 本次采用的关系含义、直接绑定及相关分支可读。
- 当判断依赖某个 operand/参与者的含义时，其对应定义必须读到；不自动读该邻居的所有边。
- 修改涉及 relation_metadata 时，提供该项完整成员及声明。
- 代码完整枚举受影响引用，但只向 Agent 提供摘要及需语义判断的正文。
- 支撑该项身份/差异/改写结论的 source 内容实际可访问，不能仅凭 source ID。

Agent 的额外读取请求只需说明：当前哪个问题、需要哪项信息、它可能改变哪个决定。Assessment 可以指出缺少的材料并要求补读，不能因 Agent 宣称 ready 就跳过。

### 3.2 三个停止门槛

1. 必需材料及已知强制比较项已处理；代码检查工具缺失、截断、未完成分页等状态。
2. 每个实质性差异都有明确处理方案，且独立 Assessment 未发现影响该决定的缺失信息。
3. 所有提案引用和必要消费者影响均有处理方式；没有未完成的原子依赖。

这是一次任务可以提交的标准，不是全库语义知识已完备的证明。普通 top-k 不承诺发现所有重复；强制端点争用不可被 top-k 掩盖。

### 3.3 读取、修改与影响三者分开

读取帮助解释；修改集合列出实际写入；影响集合由反向索引确定。纯 ID 重映射不必重新语义生成所有消费者。定义含义改变则检查直接消费者；只在消费者行为也需变化时继续传播。改写谓词定义必须检查所有使用者，不能把它伪装成局部标签修改。

关系组成员塌缩、冲突分支引用或一对多拆分不能按普通 ID 替换处理。若关系组最终只剩一条边，需判断组级知识是否已无意义、应转为单边描述或仍需其他表示，不能机械删成员并保留原文。

### 3.4 增量重检索不能只看旧邻居

新 alias 或定义改变可能让一个原来不相邻的 incoming 节点进入候选。仅重新排入旧邻居会遗漏这类匹配。

首版可以在每批提交后，对本批 seeds 和本轮改动的 canonical 重新运行便宜的候选检索；候选/相关定义/证据签名改变才调用 LLM。全局图作为检索库，不要求全图重新语义评审。索引删除导致排名变化也属于候选变化。

这会增加检索成本，但比复杂的全局语义订阅系统简单；需测成本，不宣称理论最优局部性。签名去重不能只包含候选 ID，还应包含相关定义、契约或证据变化。

## 4. 可执行接口的真实缺口

下列是当前实现事实，不是已经完成的修改：

| 位置 | 当前约束 | 与新方案的差距 |
|---|---|---|
| reconciliation/models.py | candidate 只有 NodeContent | 不能完整表达联合节点/边/契约提案 |
| reconciliation/validation.py | 每个 input ref 恰好归一个 candidate；多个 candidate 需 conflict points | 无法将一个复合来源合理重构成多个原子节点 |
| reconciliation/service.py | SEMANTIC_TYPES 只含 concept/metric/generation_rule | Event 不进入同一语义整合路径 |
| llm/tools.py | 读取某节点全部双向边，超限只提示减少 IDs | 单个 hub 超限无法通过分页解决 |
| llm/tools.py | 仅 read_nodes/read_evidence | 不能要求 Agent 完成未提供的键、NULL、重复性数据库检查 |
| GraphNode alternatives | 以节点完整内容差异表示竞争，边可从属其分支 | 不能自然承载所有纯关系或跨节点竞争 |

最小调整方向：保留现有 read 工具并增加摘要/分页；按需复用范围受限的数据库只读能力；提案支持标准节点/边操作；来源可支持多个输出，但必须通过受支持要求的覆盖审查，不能把“每来源一次”作为语义保留证明。

不要新增一套逐原子事实存储系统。既有 shared/differences/explanation/evidence_refs 可以保留，增加明确处理结论和输出对应；分析对象允许包含边或局部结构。完整候选及修改后的图仍是最终被审查对象。

最小决策记录建议如下，仅作运行时提案，不增加 ontology 属性：

```text
identity：拟整合组的共同所指，以及必须保留的身份区别
shared：共同内容
differences：difference / explanation / supporting_refs / evidence_ids
             applies_when（必要时）/ treatment / result_refs
proposal：沿用节点、边与契约操作格式
```

treatment 明确统一、补充、条件化、竞争、分离或修正；result_refs 指向这项决定实际落入的节点/边。仅对实质修改及竞争内容记录，不能扩成全图事实台账。

Identity 多对一映射与来源一对多支持必须分开：一个来源可被多个原子节点共同保留，但不能靠 `old_id -> new_id` 猜测所有消费者如何分配。来源覆盖检查实际要求是否保留，不用机械的一次分配代替。

现有 Assessment prompt 的“never invented counterexamples”也需澄清：禁止捏造事实证据；允许明确标为 hypothetical、符合既有约束的区分性输入来检验解释。不能把这种例子用作修改数据库事实的依据。

## 5. 取消 U 后仍需解决的表示问题

正常方法输出为整合图，不保留保守的 U 作为常规出口。不同 identity 保留不同节点、同 identity 的真实竞争保留 alternatives，均是明确结果。资源/工具/验证失败是执行未完成，不得自动包装成成功。

但有一个尚未闭合的设计点：节点内容完全相同，只有边断言真实竞争时，现有 node-only alternatives 未必能无损表达。不得捏造节点字段差异，不得把两个互相否定的普通边同时发布并称为已保留 conflict。

需要先做一个最小表示实验，比较两个候选方向：

- 若竞争确实属于某个业务对象的真实定义差异，沿用该节点的完整定义分支与从属边；必须说明真实归属，不能为复用容器而强行改写。
- 对独立边事实的真实竞争，评估是否可复用 compact alternatives 思路到边本身，并检查其读取、选择、引用和 relation_metadata 行为。此项是待 review 的提案，尚未批准或实现。

不能宣称边级 alternatives 自动解决任意跨节点关联分支；后一问题可能需要关联选择，必须用具体例子验证。正式支持范围和图内表示确定前，完整框架不能算设计闭合。

## 6. 首轮对抗案例

以下均是设计 mock，不是实际模型测试结果。

| 场景 | 应得结论 | 要排除的错误 |
|---|---|---|
| 同一事件时间列用于 Opening/Closure | 结合行为与参与角色区分 | 同日期字段直接合并 Event |
| 两条 Rule 分别去重与处理零分母 | 独立最小义务分别保存 | 因互补合成复合 Rule |
| 两个完整比例具有耦合的分子/分母 | 保持各自完整计算，再判 identity/条件/竞争 | 逐字段组合成无来源支持的第三公式 |
| COUNT 与 COUNT DISTINCT 恰好来自不同县 | 检查行粒度/唯一性，而不是以县作选择条件 | 把共现当解释 |
| 并列最高任选一项，两 SQL 选不同项 | 两者可能都满足同一义务 | 输出不同即判 conflict |
| A/B 相同仅由待确认的 X/Y 相同支持，反之亦然 | 查独立语义或源证据，联合审核 | 循环自证 identity |
| School 有大量边，任务只比较官网 | 摘要/分页，读取官网角色必要内容 | 无限邻域扩展或单节点 too_large 死路 |
| 新 alias 使原来不相邻 seed 成为候选 | 批次候选刷新能重新发现 | 只通知旧邻居导致永久漏配 |
| 一个复合 Rule 应拆成两个独立义务 | 来源可以对应多个输出，逐项检验保留 | exactly-once source 分配禁止正确结构 |
| 相同 node 内容下两条边真实竞争 | 在图内明确表达竞争及选择含义 | 靠正常 U、伪造 node 差异或无条件并存掩盖 |

测试应同时记录身份决策、差异解释、最终结构和 Assessment 反馈。执行一致不等于语义普遍等价，设计 mock 通过也不等于算法有效性已验证。

## 7. 下一步范围

优先完成上述判断规则及最小表示/接口试验，再跑小型受控案例。暂不增加多 Agent 运行流水线、一般 OWL reasoner、任意全图重构、全库语义订阅或大规模微型评分项。

本轮仅沉淀审查发现与修订建议。纯关系真实冲突等表示选择仍需明确，不通过给审查者反复要求“通过”来消除真实缺口。

## 8. 最终审查汇总

- 语义审查：方向合理，身份/兼容性、互补/原子性、条件化与真正竞争需要上述收紧；纯关系竞争仍是待决表示边界。
- 边界审查：按必需读取记录与独立 Assessment 控制停止；补批次候选刷新，分开机械引用与语义传播后，可进入小规模验证。
- 可执行性审查：必须允许来源一对多、修正 coverage 的对象、补工具分页和 Event 语义入口；纯边竞争未解决前，不应标记完整设计通过。

三个审查者均未运行真实 merge 实验或修改生产代码。本文是主 agent 对发现的整理及拟采纳修订，不把需要用户 review 的表示扩展记作已确认设计。
